## 一、五个 Skill 的职责边界总表

| Skill | 类别 | 核心职责 | 不做的事 |
| --- | --- | --- | --- |
| video-editing | 主 Skill | 理解任务、选择与组合方法、协调范围与冲突、组织交付 | 不内置全部口播/卡点/教程细节 |
| footage-intake | 通用流程 | 检查素材、组织转写与按需画面、形成摘要和缺口 | 不对每个素材无差别跑全部模型 |
| revise-edit | 通用流程 | 读最新版本、限定目标、保护非目标修改、形成局部提案 | 不默认重做整片 |
| render-qa | 通用流程 | 按 manifest 检查文件、关键内容和待审片项 | 不只看退出码或字幕某词 |
| talking-head-roughcut | 首个专项 | 按讲话内容选段、去重复/停顿、组织顺序、保护语义 | 不成为所有视频的强制入口 |

来源：PRD §8.1/§8.2；总览 §2；技术手册 §8.2/§8.7。

## 二、五张场景卡

以下成功样例均为待验证的设计场景，不代表已运行。实际测试须登记夹具引用/hash、初始工程版本、用户请求、保护项、预期轨迹与断言，并保存结果和证据位置；场景 ID 用于关联测试记录，不提前固定底座 schema 或真实工具名。

### video-editing

#### 一句话功能
视频任务的主协调者：整理简报、按需选择与组合方法、协调作用范围与冲突、推进到可检查的交付。

#### 触发条件
- 应选择：新建或继续视频任务时作为入口方法加载；需在多个方法间选择、组合或处理范围冲突时；需整理创作简报、编排任务或组织交付时。
- 不应选择：试图用它执行某专项的全部细节（如口播逐句判断）。当前任务已加载主 Skill、现场与目标未变且某通用流程可独立推进时，无需重复加载主 Skill；目标、范围或版本发生关键变化时重新核对现场。

#### 前置输入
- 需要：用户目标、素材路径或已有工程引用、已明确的保留项；继续项目时读取 projectId、currentRevision、选择与任务状态。首次新建允许尚无 projectId/revision，由项目创建与素材入库能力补齐，不要求用户先手工建好工程。
- 缺目标时先澄清影响执行的要求；未额外指定保留项时记录该事实并沿用已有约束，不把“没有新增保留项”当作阻断。普通缺省项采用可见默认值；缺能力摘要时先查询能力目录（capability list 这一组逻辑工具）。

#### 工作步骤
1. 区分首次新建与继续项目：首次经项目创建能力取得身份，再按需安排素材入库；继续时读取当前项目头、选择、未完成任务与已接受修改，确认当前版本。
2. 整理创作简报：区分明确要求、可见默认值、推断与待定冲突；记录用户本次要求是分析、先给方案还是执行剪辑，避免越过授权提交。
3. 按任务和缺失前置能力选择方法：新素材、分析失效或证据不足先进入 footage-intake；讲话粗剪进入 talking-head-roughcut；局部反馈进入 revise-edit；已有产物或检查阻断进入 render-qa。已有有效分析可复用，不强制每次从头跑完整流程。
4. 涉及核心表达冲突或放弃保留项时，给出可比较选择，停下等用户确认；普通默认值与不影响核心表达的推断明确展示后继续推进。
5. 只做分析时产出简报/观察；涉及编辑时组织方法形成统一提案，由同一 Agent 在主流程中按本次授权安排校验和提交。用户要求“先给方案”时只返回提案；获准执行时每次逻辑修改只提交一次，不能由专项与主流程重复应用。
6. 组合多个方法时先定分工与保护范围；第一份提案提交成功后读取服务返回的新 revision、diff 与对象映射，再核对第二份。版本、时间、保护范围与幂等由共同服务强制校验，不能由 Skill 自行绕过。
7. 按需要经 render submit 固定清单并提交预览/导出，通过 job control 查询、等待、取消或核对失败/中断任务；不把提交成功当成产物完成。产物就绪后进入 render-qa，遇阻断时整理原因和下一步；交付引用其检查结论，说明版本、产物、待审片项与已知限制。

#### 保护与冲突
- 必须保留项、事实与语义完整性优先于未经授权的时长压缩；改变核心表达或放弃保留项需用户决定。
- 两方法争同一对象时不并行盲目应用；先提交一份，读新版本再核对第二份。方法负责形成与解释提案，共同服务负责原子提交、保护约束、幂等、历史与变更事件。
- 能力缺失或任务失败时不假装完成，保留已有有效结果，说明缺口、可验证的替代路径与停止条件；运行结果不明时先核对，不重复启动任务。

#### 所需能力
逻辑能力——项目创建与现场读取、能力目录、提案校验与应用、按需渲染提交、任务查询/取消/恢复核对、产物证据读取。按当前步骤检查就绪状态，不因本次不需要的能力缺失而阻断整个任务；缺必要能力时说明实际原因。逻辑工具名以锁定版本的真实接口为准，不视为已实现。

#### 输出类型
简报（分析）、统一提案（待提交）或已授权修改的提交结果引用（含 newRevision、diff、affectedIds）；长任务输出 job 与所属版本引用。交付阶段输出交付说明，引用 render-qa 报告，区分已验证、阻断与待人工审片，不自行断言产物合格。

#### 成功样例
- 场景 ID：SC-VE-01；关联 AC-06、AC-07、AC-10。设计样例，尚未运行。
- 输入与初始状态：用户提供六分钟产品讲解，要求约一分钟、保留产品名与使用限制，首次进入时没有 projectId；实际夹具须登记文件引用/hash、保留内容来源与时长允许偏差。
- 预期轨迹：创建工程与检查能力→footage-intake 补齐必要分析→加载口播专项形成提案。若用户要求“先给方案”，到提案即止；获准执行后只提交一次，再按需提交导出、查询任务并交 render-qa 检查。
- 通过断言：保留项有来源引用；时长冲突可见且未经决定不放弃保留项；未加载专项不声称使用；重复任务请求不新增重复执行；交付的任务、清单与产物版本一致。
- 失败分支与证据：缺必要能力时返回真实状态和下一步；核心取舍未决时等待用户。留存实际加载的 Skill 来源/hash、工具轨迹、提案、提交与任务/验收引用。（依据 PRD §5.5 贯穿验收示例）

#### 反例
所有视频都走口播方法；首次新建因没有 projectId 被直接拒绝；未加载专项正文就声称已使用；用户只要方案却提交修改；专项和主流程重复应用；导出刚提交就报告完成。

#### 人工检查点
执行前：核心表达取舍、放弃保留项或无法可靠理解的范围需用户决定；普通默认值与不影响核心表达的推断可见记录后继续。交付后：用户审片判断节奏、自然度及是否接受；人工审片未完成时不标注“用户已接受”。

#### 与其他 Skill 的边界
主 Skill 组织方法选择、授权判断、唯一一次提交与长任务闭环；不代替 footage-intake 的素材检查、revise-edit 的局部提案、render-qa 的检查或专项的选段判断。五份方法由同一 Agent 按需读取，不是另开五个 Agent；运行与一致性约束由服务和工具实现。

#### 来源
PRD §8.1/§8.2/§8.3、§5.1/§5.2/§5.4、§7.1（AG-01/AG-04/AG-05/AG-08）；技术手册 §5.1、§6.2/§6.3/§6.4、§7.3、§8.2/§8.7；总览 §2。

#### 假设与待确认
- [推断] 主 Skill 正文在 M1 只需最小协调规则，专项细节随能力补齐。
- [推断] 入口配置能否保证模型实际加载主 Skill，需 M0/M1 真实轨迹验证（技术手册 §7.1）。

### footage-intake

#### 一句话功能
素材接收与初查：检查可用性、组织转写与按需画面、形成可回查摘要和缺口报告。

#### 触发条件
- 应选择：用户提供尚未入库的素材路径/URI、新素材加入项目、用户补充或更换素材时；已有分析失效或信息不足以支撑选段时。
- 不应选择：素材已入库且相关分析仍有效、本次局部修改无需补充证据时。未入库素材由本流程调用 media intake 完成入库与探测，不要求用户先手工导入。

#### 前置输入
- 需要：原始路径/URI 或已有 assetId、目标用途与已知保留项。未入库时经媒体能力取得 assetId、内容 hash 与媒体流规格；需要新建工程时由主流程先取得 projectId，不要求输入中已具备全部探测结果。
- 缺必要转写/探测能力时记录能力目录返回的实际状态与原因；已有分析要核对素材 hash、实现版本和适用条件，失效才重做。缺时间精度时限制后续精细切点能力，不阻断仍可可靠完成的粗粒度分析。

#### 工作步骤
1. 对未入库素材调用 media intake；对已有素材读取并核对身份与探测记录：容器、编码、时间戳、声道、帧率、原点，不凭扩展名或文件名判断。
2. 检查 VFR、旋转、缺音轨、静音及中文/空格路径的兼容条件。需要规范化时经媒体能力生成工作媒体，保留原素材、转换参数、时间原点、旋转/音画偏移处理与源/工作媒体映射；已支持的处理策略可记录后执行，存在取舍时再确认。
3. 按目标需要提交转写或其他分析（analysis submit/read）：讲话内容需要核对时获取相应转写，非讲话素材不强制完整转写；长任务保留 job 引用，读取完成结果后才作为证据，必要时由主流程核对失败或取消。
4. 标明转写时间精度、缺失与不确定项，并明确分析引用原素材还是工作媒体；句级时间只能支持经核对的句级边界，不声称精确切词。
5. 按需读取画面（media inspect）：读取核对保留内容或关键操作所需帧/短预览，保留来源引用，不无差别全量抽帧。
6. 形成可回查摘要：可检查区间、来源时间与坐标系、质量问题、缺失信息均带引用；提供素材观察，不把候选区间直接当最终剪辑决定。
7. 报告可继续、需补证据与阻断的范围：素材不足、转写缺失、精度不足时说明可验证替代路径或所需人工标注；不可用步骤停止，其他独立可用步骤可继续。

#### 保护与冲突
- 原素材只读，不修改；工作媒体转换保留参数与映射记录。
- 转写结果与字幕纠正分开保存，纠正不写回原始识别。
- 静音/缺音轨素材不能强行当口播处理。

#### 所需能力
媒体导入/探测与按需规范化、必要的分析提交与读取、按需画面检查。依实际返回区分 available、notConfigured、missingDependency、incompatible 等状态及原因，不把所有缺失硬写为 notConfigured；状态名称以实际能力契约为准。

#### 输出类型
观察/简报（素材身份、媒体/分析引用、时间精度、可回查摘要与缺口），必要时附 job 和工作媒体映射引用。入库及分析记录经共享能力/服务保存；本流程不直接改写剪辑时间线。

#### 成功样例
- 场景 ID：SC-FI-01；关联 AC-06、AC-09。设计样例，尚未运行。
- 输入与初始状态：一段尚未入库的手机竖屏 VFR 录像，带旋转标记，路径含中文与空格；实际夹具须登记原文件引用/hash、探测基准与待核对的保留内容。
- 预期轨迹：入库并取得 assetId→探测→必要时生成 CFR 工作媒体及映射→提交并读取转写→按需核对画面→形成摘要；测试可使用明确标注的句级转写夹具，但不能据此声称 ASR 效果通过。
- 通过断言：原文件 hash 不变；工作媒体有独立身份和转换/映射引用；旋转、原点与音画偏移处理可核对；句级精度被明确记录，后续不生成未经验证的字级切点。
- 失败分支与证据：无音轨不强行转写；能力缺失按真实状态报告；映射无法验证时不发布为可可靠剪辑的分析。保留探测、转换、job/分析、摘要与核对证据。（依据 PRD §3.3、技术手册 §4.2）

#### 反例
把尚未入库当作本流程不能触发的理由；把完整探测日志塞给模型；把句级时间当成字级切点；工作媒体生成后丢失原素材映射；只提交分析任务就报告已拿到结果。

#### 人工检查点
执行前：只有会影响素材含义、质量或支持范围的处理取舍才需确认，常规已支持的规范化记录策略后推进。结果复核：抽查关键实体、数字、否定词与保留项覆盖；时间或内容无法确定时请求必要标注，不要求用户逐项复核全部日志。

#### 与其他 Skill 的边界
负责导入、探测、分析与证据整理的编排，具体执行由共享能力完成；不做最终内容选段（交 talking-head-roughcut 或其他适用方法），不直接修改时间线，不代替 revise-edit 或 render-qa。主 Skill 负责跨方法协调与任务交接。

#### 来源
PRD §8.2、§3.3；技术手册 §8.2/§8.7、§5.1、§4.2；总览 §1.2、§4.2。

#### 假设与待确认
- [推断] 首版转写只接一条中文路径（ADR-003 待定），精度与覆盖以实测为准。
- [推断] 按需画面的读取粒度与 token 预算需 M2 真实任务校准。

### revise-edit

#### 一句话功能
局部修改：读最新版本、解析用户指向或选中对象、限定修改范围、保护非目标修改、形成局部提案。

#### 触发条件
- 应选择：用户针对选中对象、明确范围或可结合当前工程理解的局部指向提出修改时（如“缩短开头五秒”）；反馈要求局部调整时。
- 不应选择：任务已变成整片结构重组时（交主 Skill 重新组织）；修改指向有歧义且无法可靠消除时先澄清，不据此默认重做整片。

#### 前置输入
- 需要：projectId、用户修改目标、当前工程与已接受修改；有显式选择时包含 observedRevision、selectionType、稳定对象 ID、范围及坐标系。currentRevision 由服务读取，不把用户或聊天中保存的版本号直接当最新版本。
- 无显式选择时先结合工程解析自然语言指向，记录解析出的稳定对象与范围；有歧义或对象删除/拆分后无法通过可靠映射定位时，才要求用户补选或澄清。播放头不自动等于编辑选择。

#### 工作步骤
1. 读取最新工程（project read），确认 currentRevision、当前内容与已接受修改，不从旧聊天或旧提案推测现场。
2. 校验显式选择或解析自然语言指向；observedRevision 过旧、对象删除/拆分时，先读取服务提供的稳定对象映射。无法可靠定位时再要求补选或澄清，并保留原请求。
3. 明确修改目标、来源/成片坐标系与作用范围；用户只要求方案时不提交，范围或目标发生变化时由主流程重新核对授权。
4. 检查非目标区的人工纠正与其他已接受修改，标为保护范围；用户明确要求修改的目标文字可以修改，但不能顺带覆盖其他纠正。
5. 形成局部统一提案：projectId、baseRevision、scope、候选 operations、evidenceRefs、protectedRefs 与 unresolved 按共同契约表达。baseRevision 使用此次读取的版本；交主流程安排唯一一次服务校验与已授权提交，提交时由服务再次原子比较基准。
6. 涉及字幕/片段重排或裁剪时，在提交校验中要求服务验证来源与纠正映射；无法可靠映射则拒绝该提案，保留当前工程并报告缺口，不先提交破坏性结果再要求用户重新选择。成功后读取 diff 与对象映射，核对目标生效和保护项保持。
7. 区分传输重试与版本冲突：传输重试沿用同 commandId、同 payload，并先核对不明确的执行结果；版本冲突后重读并重新理解，形成新命令与新 commandId，不能只改 baseRevision 强行重放旧提案。恢复旧内容同样经服务产生新 revision。

#### 保护与冲突
- 非目标的人工纠正与已接受修改必须保留；用户明确要求修改的目标内容按本次范围处理，不把保护规则变成禁止用户改自己的内容。
- 为缩短开头不能删掉后面的限制说明；涉及否定、数字、条件的语义取舍需核对来源，必要时交用户决定。
- 基准过旧时重新核对，不静默覆盖；原子版本比较、幂等、对象/字幕映射与恢复新版本由共同服务保证，Skill 不能靠提示词宣称这些约束已成立。

#### 所需能力
读取项目与历史、解析/校验选择及稳定对象映射、提案校验与应用、差异与按需恢复读取。缺必要的版本/保护/映射校验时可形成带缺口的待验证提案，但不能提交受影响修改；同 ID 同内容重试与同 ID 异内容拒绝由服务强制执行。

#### 输出类型
统一提案（待提交），包含目标与保护范围、来源依据和未决项。获准提交后由主流程关联服务返回的 newRevision、diff、affectedIds 与映射/验证结果；未执行或提交失败时明确记录状态，不将提案当作已生效修改。

#### 成功样例
- 场景 ID：SC-RE-01；关联 AC-01 至 AC-05。设计样例，尚未运行。
- 输入与初始状态：用户已把产品名字幕纠正并保存到 r13，Agent 手中仍有基于 r12 的提案；用户未选中片段，要求“缩短开头五秒”。实际夹具须登记工程/素材引用/hash、纠正对象 ID、可安全缩短区间与受保护限制说明。
- 预期轨迹：服务拒绝旧基准且内容不变→Agent 读取 r13 并解析开头范围→形成新的局部提案与命令→主流程按授权校验/提交→读取差异，按需预览与重开核对；不要求用户为清楚的指向额外补选。
- 通过断言：开头在有足够可删内容时按要求缩短；产品名纠正与后续限制说明保持；传输重试不重复缩短，同 ID 不同内容被拒绝；恢复旧内容生成新的、不复用的 revision；重开恢复正确内容与版本。
- 失败分支与证据：若五秒内含必须保留语义，提供取舍并等待决定；映射不明时不提交。留存旧基准拒绝、最新读取、提案/命令关联、diff、重试/恢复及重开证据。（依据 PRD §5.3、技术手册 §8.9）

#### 反例
用旧基准覆盖；只改版本号重放旧提案；清楚的“缩短开头”也强制用户补选；把用户明确要求修改的旧纠正一律锁死；为缩短开头删掉后面的限制说明；映射失败仍提交，导致字幕纠正错位。

#### 人工检查点
执行前：修改范围有歧义、无法可靠定位或与保留项冲突时需用户澄清/决定。结果复核：检查目标是否生效、非目标区域和纠正是否保持、语义是否完整；可由程序验证的版本、差异和映射先看服务证据，不逐次要求用户替代技术校验。

#### 与其他 Skill 的边界
不做整片选段（交专项）；不做素材检查（交 footage-intake）；不做产物验收（交 render-qa）。

#### 来源
PRD §8.2、§5.3；技术手册 §8.2/§8.7/§8.9、§4.4、§9.2；总览 §4.3/§4.4。

#### 假设与待确认
- [待验证] 字幕实例映射在 M1 确定最小契约和拒绝行为，M2 用真实重排/裁剪样例验证；不能到映射失败后才补保护策略。
- [待验证] 选择上下文、自然语言指向与源/成片坐标的具体映射按所选编辑底座在 M1 联调；播放头不等于选择，只有可靠映射才可执行（技术手册 §9.2）。

### render-qa

#### 一句话功能
产物验收：按 renderManifest 检查文件层、内容层与人工审片层，形成问题与修正建议。

#### 触发条件
- 应选择：预览或导出产物就绪后；需核对指定版本与清单，或需要形成“产物缺失/未就绪、任务失败、检查条件不足”的阻断报告时。
- 不应选择：用它替代渲染执行、任务控制或时间线修改。不得用当前最新工程验收旧成片；遇此情况应转为按原 manifest 检查，无法取得则报告阻断。

#### 前置输入
- 正式验收需要：renderManifest（projectId、revision、工程快照及 hash、媒体/字幕/字体等依赖 hash、输出规格与实现版本/参数）、产物引用，以及可回查的保留项和来源依据；必要时读取 job 与先前检查记录。
- 缺 manifest 或产物时仍可给出有限诊断与阻断报告，但不能宣称对应版本验收通过；明确哪些检查未执行。产物所属版本与当前工程不同并非自动失败，只按 manifest 所属版本验收并显示当前版本差异。

#### 工作步骤
1. 读取清单、产物与必要任务状态，确认版本、文件可用性和证据完整性。产物未生成、任务失败/取消或状态不明时输出有依据的阻断/待核对结果，由主流程处理等待、取消或恢复，不把中间文件当成品。
2. 文件层检查（artifact verify/read）：实际解码、预期帧数、画幅、音轨与字幕产物；音频采样、起点与编码延迟采用已明确的容差，不只看退出码、文件存在或容器总时长。
3. 内容层检查：依据保留项与来源核对指定语义、句子和画面，记录证据与无法确定的部分；字幕出现产品名不独立证明原声保留，来源片段正确也不独立证明渲染正确。
4. 区分版本归属：r1 渲染期间编辑到 r2 时，只用 r1 的冻结清单与依赖检查成片，报告标明“来自 r1，当前工程 r2”，不为匹配当前工程而改写旧清单。
5. 缓存复用时验证产物存在、完整、hash 和适用条件，确认清单绑定正确；复用也建立当前任务与清单的验收引用，不能仅凭 revision 或文件名判定缓存有效。
6. 列出待人工看/听/判断项及其具体范围（节奏、自然度、字幕观感等）；程序已通过、内容未确定、人工未审分别记录，不用“需人工”掩盖未执行的技术检查。
7. 形成报告：逐项记录通过、失败、未验证/阻断和待人工审片，带检查范围、证据与修正建议；按实际结果区分技术验收、内容判断与用户接受，不合并成一个无依据的“成功”。

#### 保护与冲突
- 不拿当前最新工程验收旧成片；没有足够清单与证据时只能给出有限诊断，不能补造版本归属。
- 退出码为零、文件存在不等于成功；未完成文件不进入作品库，必要检查失败或未完成时不标记验收通过。
- 技术探测由工具执行，发布与任务状态转换由服务负责；Skill 组织证据与报告，不直接修改产物、清单或时间线。人工审片与用户接受分别保留。

#### 所需能力
产物探测与读取、清单读取、任务状态读取。缺探测能力时不能断言合格。

#### 输出类型
检查报告或阻断报告，包含项目/版本/manifest 与产物引用、检查范围、逐项结论、证据、待人工判断项和修正建议；缺清单时说明版本验收未执行。报告本身不修改时间线，修正建议交主 Skill 或 revise-edit 形成新提案。

#### 成功样例
- 场景 ID：SC-RQ-01；关联 AC-07、AC-08、AC-09。设计样例，尚未运行。
- 输入与初始状态：r1 的冻结 manifest 与导出任务，运行期间工程编辑到 r2；实际夹具须登记工程、媒体/字幕/字体依赖、输出规格与产物引用/hash，以及预期帧数、音频容差和保留项基准。
- 预期轨迹：读取任务与 r1 清单→真实解码与文件检查→核对保留内容→检查复用条件→形成仅属于 r1 的报告，展示当前为 r2。
- 通过断言：清单与依赖不因 r2 编辑而改变；文件/内容结论有证据；复用有效缓存仍关联本次任务与清单；人工未审不标记已接受。
- 失败分支与证据：缺产物、缺 manifest、任务失败/取消或解码失败时保留实际状态与日志，报告阻断而非通过；不得将半成品发布。保存清单、探测/内容检查、缓存引用与报告。（依据 PRD §5.4、技术手册 §6.1、AC-07）

#### 反例
用 r2 验 r1；缺 manifest 仍给出版本验收通过；产物未生成就不再报告任务阻断；字幕出现产品名就断言原声保留；只看退出码零就报成功；用户未审片却标记已接受。

#### 人工检查点
技术检查先由工具提供证据；人工审片重点为内容语义、节奏、音画观感、字幕可读性与是否接受。报告要定位待审范围，并区分已完成技术检查、待人工判断与用户最终接受，不默认每个技术步骤都需用户确认。

#### 与其他 Skill 的边界
检查产物与证据、形成验收或阻断报告；不执行渲染/取消/恢复，也不直接改工程。主 Skill 编排任务控制与交付，修正由主 Skill 或 revise-edit 形成新提案，经共同服务校验和已授权提交。

#### 来源
PRD §8.2、§5.4；技术手册 §8.2/§8.7、§6.1、§5.1；总览 §5.1、§8.1；AC-07。

#### 假设与待确认
- [推断] 文件层检查的具体容差（音频采样率、编码延迟）需 ADR-002 确定后细化。
- [推断] 人工审片项的量表需 M3 联合验收时固定。

### talking-head-roughcut

#### 一句话功能
口播粗剪专项：按讲话内容选段、处理重复与停顿、组织顺序、保护否定/数字/条件/限制说明。

#### 触发条件
- 应选择：本次作用范围以讲话内容为主、任务需要粗剪口播时；教程/产品视频中的讲话部分可按相同条件复用，并保护用户标注或已核对的操作画面与其他非目标范围。
- 不应选择：把非讲话主导的完整教程/产品视频强行交给本专项；无可追溯转写或标注时直接生成可执行选段；时间精度只够粗切却声称精确切词。证据不足先补分析，句级证据足够时允许经核对的句级粗剪。

#### 前置输入
- 需要：projectId 与当前工程版本、讲话范围、可回查转写或已核对标注（含素材/工作媒体引用、时间坐标、精度与缺失项）、目标时长及允许偏差、明确保留项与已有人工纠正。
- 缺必要转写/来源证据时交 footage-intake 补齐，或取得可验证的人工标注；时间精度不足只限制受影响的切点粒度。未指定精确时长时由主流程记录可见目标，不要求用户为普通缺省项反复确认。

#### 工作步骤
1. 读取当前工程、讲话范围、转写/标注与目标，确认版本、来源坐标与时间精度；证据不足先补齐，句级证据不生成未经核对的字级切点。
2. 按讲话内容识别可用段、重复表述与长停顿；结合上下文区分赘述、强调和必要解释，不只按静音或固定阈值机械删除。
3. 逐项保护否定、数字、条件、限制说明和明确保留项，保留已有非目标字幕纠正；教程/产品任务还核对受保护的操作画面与讲解关联，不只保留声音。
4. 按本次表达目标组织顺序，形成连贯结构与候选片段；“问题—操作—结果—限制”只是可选示例，不强制套用，重排后核对指代、因果与上下文。
5. 计算可检查的预估时长并列出来源区间、保留/删除依据和不确定项；时长与保留项冲突时给出取舍，不暗中删保留项或扩大作用范围。
6. 形成统一提案：projectId、baseRevision、scope、候选 operations、evidenceRefs、protectedRefs 与 unresolved 按共同契约表达；交主流程按授权安排校验和唯一一次提交，不自行重复应用。时间合法性、保护范围与版本由服务强制校验。
7. 素材/转写不足时提出补证据或人工标注需求；基准冲突时读取新工程并重新核对候选，不只改版本号重放。提交成功后核对差异及保留项，按需要请求短预览并交 render-qa 检查，不由本专项自行宣告成片合格。

#### 保护与冲突
- 必须保留项优先于时长压缩；不为时长删保留项。
- 不截断句意；不照搬示例时间码。
- 与其他专项组合时只处理讲话范围，不截断受保护讲解。

#### 所需能力
当前工程与转写/标注读取、按需来源回看、提案校验、差异与必要短预览；选段与内容取舍由 Agent 判断，实际修改与媒体执行由主流程调用共同服务。缺必要证据或时间精度时限制对应步骤，未达到执行条件的只返回候选与缺口，不冒充可执行提案。

#### 输出类型
统一提案（待提交），附选段顺序、来源与保留/删除依据、预估时长、保护引用和不确定项；证据不足时返回候选观察与缺口。获准提交后的结果由主流程引用服务回执，不把建议、执行成功与成片验收混为一体。

#### 成功样例
- 场景 ID：SC-TH-01；关联 AC-06、AC-09；限定范围组合另关联 AC-10。设计样例，尚未运行。
- 输入与初始状态：一人讲话六分钟，包含多次重录、长停顿、数字、否定与使用限制；实际夹具须登记媒体/转写引用与 hash、时间精度、保留项来源、目标时长与允许偏差，必要时注明需保持的操作画面。
- 预期轨迹：读取最新工程与证据→提出内容结构与来源选段→检查保留项和预估时长→形成统一提案；获准提交后读取差异，按需预览并交验收。
- 通过断言：保留项逐项可回查，选段前后语义一致；不误删否定、数字或限制说明；重复/停顿处理有内容依据；切点符合证据精度，且非目标人工修改与画面保持。
- 失败分支与证据：目标时长不可满足时提出取舍，不偷删保留项；来源或精度不足时不提交受影响片段。保存实际选段依据、提案、差异及预览/检查引用，人工再判断节奏与自然度。（依据 PRD §2.2、§5.5）

#### 反例
为时长删掉使用限制说明；截断否定句意或改变数字含义；照搬文档示例时间码；把示例内容结构强制套给所有口播；只保留讲解却删掉受保护操作画面；句级证据声称精确切词。

#### 人工检查点
执行前：只有核心表达、明确保留项或目标时长不可兼容时需用户决定。结果审片：核对保留内容、上下文连贯、节奏与自然度；来源定位、时长和差异先提供工具证据，不用用户审片代替技术检查。

#### 与其他 Skill 的边界
只负责指定讲话范围内的内容选段，不代表整个产品仅支持口播。素材/证据补齐交 footage-intake，已接受工程的局部调整交 revise-edit，产物检查交 render-qa；主 Skill 负责组合、授权与提交。非讲话任务可按现有能力和人工标注处理，新增自动化专项仍需独立验证。

#### 来源
PRD §8.2/§8.3、§2.2、§5.5；技术手册 §8.2/§8.7/§8.8；总览 §2。

#### 假设与待确认
- [范围说明] 本专项适用于讲话主导的片段；首版产品仍覆盖 PRD 约定的口播、简单教程与产品任务。非讲话部分的支持按当前能力与可核对标注确定，不能据本专项边界擅自缩小产品范围或承诺未来专项已交付。
- [待验证] 重复、停顿与切点判断需 M2 真实样例校准，参数按素材与目标调整；不能把单个样例的阈值升级为全部任务的固定规则。

## 三、跨 Skill 的组合与冲突规则

1. **选择顺序**：任务开始或恢复时先加载 video-editing，由同一 Agent 按任务与缺失前置条件选择方法；首次项目创建与未入库素材由主流程/footage-intake 调用相应能力补齐。当前任务已加载且现场未变时不重复加载主 Skill；不假设五份正文自动注入，也不把五个 Skill 当作独立 Agent。

2. **分析与编辑分离**：footage-intake 组织入库/分析并产出观察，render-qa 产出检查或阻断报告，二者不直接修改剪辑时间线；revise-edit 与 talking-head-roughcut 形成共同提案。提案含项目、基准版本、范围、候选操作、证据、保护项与未决项；主流程按本次授权安排唯一一次校验/提交。用户只要分析或方案时不提交，自然语言说明不等于可执行提案。原子版本、幂等、历史和映射由服务保证。

3. **组合规则**：多方法组合时先定分工与保护范围。第一份提案提交成功后读服务返回的新 revision、diff 与对象映射，再核对第二份；内容冲突返回协调，映射不可靠则不提交受影响修改。例如口播方法整理讲解后，第二专项只处理指定 B-roll，不改变受保护讲解音轨、字幕和操作画面。

4. **切换规则**：同一项目切换方法时沿用当前工程与已接受编辑，读取最新版本并复用仍有效的分析，不恢复旧快照覆盖人工操作。Skill 读取是获取方法指令，不等于函数调用或已执行工具；实际步骤以可用工具及其结果为准。

5. **冲突处理**：两方法争同一对象时不并行盲目应用；保护非目标人工修改，用户明确要求修改的目标内容可按本次范围调整。保留项、事实与语义完整性优先于未经授权的时长压缩；核心取舍或范围无法可靠确定时再等待用户，普通默认值可见记录后继续。传输重试沿用同 ID 同内容；版本冲突重新核对并形成新命令，不只改基准号重放。

6. **能力门控**：按步骤采用能力目录实际返回的就绪状态、原因与限制，不把所有缺失都写成 notConfigured；缺必要能力时不执行受影响步骤，但可继续独立可用部分或给出有限诊断。普通导入/规范化不改变时间线，编辑仍经共同入口。只有一个口播专项时，用受控夹具验证方法选择、范围组合、方法切换与缺能力四类情况（AC-10）；夹具通过只证明接口，不宣称真实第二专项已交付。

7. **交付闭环**：主流程按需提交绑定冻结清单的预览/导出，负责查询、有限等待、取消和失败/重启核对，不把提交当完成；状态不明时先核对，不重复启动。render-qa 对就绪产物给检查结论，对缺产物/清单给阻断报告；主 Skill 引用报告组织交付，区分技术检查、内容判断与用户接受。修正建议形成新提案，经授权提交；不强制每次局部改字都重跑全部分析和渲染。

来源：PRD §5.2/§5.3/§5.4、§8.3、§11.1；技术手册 §4.3/§4.4/§4.5、§5.1/§5.2/§5.3、§6、§8.8、§9.2；总览 §2、§5。
