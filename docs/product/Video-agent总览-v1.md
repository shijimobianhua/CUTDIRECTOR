# Video-agent 总览

- 版本：v1
- 日期：2026-11-01
- 定位：本项目的总纲。上游依据为 [视频Agent整体方案与参考项目.md](<./outputs/视频Agent整体方案与参考项目.md>) 与 [视频AgentSkill架构.md](<./outputs/视频AgentSkill架构.md>)，本文不重复论证，只回答三件事：**先做什么、做到什么程度算完、AI 写代码时边界在哪。**
- 读者：项目负责人（做决策与验收）、执行 AI（按任务卡写代码）。

---

## 0. 使用方式

1. 每次开一个新的 AI 会话，先让它读本文件的第 3、4、5、6 章，再读当次要做的任务卡。
2. 任务卡（如 `M1-T3`）是**最小执行单元**：一张卡一个会话，做完即验收，不跨卡施工。
3. 修改本文件需要升版本号（v1 → v1.1），并在文末“变更记录”写一行。
4. 本文与两份上游文档冲突时，以本文为准；与真实素材测试结果冲突时，以测试结果为准并回写本文。

---

## 1. 一句话定位

给中文个人创作者的口播/教程/产品视频 Agent：**同一份可编辑工程**，Agent 改、人也能改，改完还能继续。

最终形态分三层，但建设顺序倒过来：

| 层 | 最终形态 | 建设时点 |
|---|---|---|
| 内核 | 工程 + 编辑命令 + 任务 + 媒体执行（无界面） | 最先（M1） |
| Agent | Skill + 工具 + 会话编排 | 其次（M3） |
| 工作台 | 页面：作品库、播放器、时间线、字幕 | 再次（M4–M5） |
| 独立端 | 桌面壳 / 独立入口 | 最后（M6） |

---

## 2. 三条核心判断

### 2.1 先做内核，不是先写 Skill

没有“项目 + 命令 + 版本”，Agent 只能一次性生成 mp4：用户改完字幕它就接不上，旧方案会覆盖新修改，工作台也无从下手。**Skill 是方法，内核是事实来源。** 所以 M1 不接任何模型也要能端到端跑通。

### 2.2 UI 后置，但契约前置

M4 的工作台只是 M1 契约的第二个客户端。判断标准：**M4 上线时不需要改 host 逻辑**，只加页面与路由。做不到，说明 M1 白做。

### 2.3 全程 AI 写代码 → 边界必须机器可验证

人给方向与验收，AI 给实现。因此每个任务卡必须有**可执行命令的验收**，而不是“看起来对”。凡是“只能靠人眼判断”的东西（节奏、观感、选段好不好），单独列为人工验收项，不混进代码验收。

## 3. 总体架构

### 3.1 分层

```
┌─────────────────────────────────────────────┐
│ 客户端：DSH 页面（M4+）/ 桌面壳（M6）          │
├─────────────────────────────────────────────┤
│ DSH 插件层：cordis.patch.yml + host 入口      │
│   skills / tools / jobs / webServer 路由     │
├─────────────────────────────────────────────┤
│ 内核（与 DSH 解耦，可单测）                    │
│   project · commands · versions · jobs       │
├─────────────────────────────────────────────┤
│ 能力适配器：ffmpeg / ASR / OCR / 视觉 / 渲染   │
├─────────────────────────────────────────────┤
│ 存储：workspace/projects + $DSH_HOME 索引     │
└─────────────────────────────────────────────┘
```

**边界铁律**：内核不 import DSH、不 import React、不读环境变量以外的全局状态。这样 M6 换壳时内核原样搬走。

### 3.2 三个契约（本项目的地基）

| 契约 | 文件/接口 | 谁写 | 谁读 |
|---|---|---|---|
| 工程 | `project.json`（schema 固定） | 内核 | Agent、UI、渲染、校验 |
| 编辑命令 | `apply(cmd, baseVersion)` | 内核 | Agent 工具、UI 操作 |
| 任务 | `job` 记录 + 状态机 | 内核 | Agent、UI、CLI |

三者之外的一切都是实现细节，AI 可以自由发挥；三者本身**只能由人批准后修改**（见 6.4 红线）。

### 3.3 一次修改的完整路径

```
用户/Agent 提出修改
  → 形成 command（带 baseVersion、目标对象、参数）
  → 内核校验（schema、时间码、版本、权限）
  → 生成新 version + diff
  → 需要渲染则提交 job（异步）
  → job 产出 artifact + 回读校验报告
  → UI 与 Agent 读同一份 project + version
```

任何绕过这条链路的写入，都视为 bug。

### 3.4 时间与坐标基准（M0 定，不可反复）

- 内部统一用**帧号**（整数）+ 项目 `fps`；显示层再转 timecode。
- 源素材保留**微秒级 sourceTime**，与帧号双记，避免不同帧率素材漂移。
- 字幕、选段、关键帧一律引用源时间；进入成片时通过一张**映射表**转到输出时间轴。
- 变速、转场、多机位在 M5 之后再扩展映射，不在 M1 假装支持。

## 4. 里程碑总表

| 里程碑 | 目标 | 主要交付 | 退出验收 | 预估（单人+AI） | 人工投入 |
|---|---|---|---|---|---|
| **M0** | 钉死不可逆决策 | 4 份 ADR + 1 个 spike | spike 跑通真实素材 | 3–5 天 | 高（做决定） |
| **M1** | 无头内核 | project/commands/jobs/ffmpeg/CLI | 改→回滚→再改，工程可重开 | 2–3 周 | 中（验收） |
| **M2** | 素材理解 | 转写、摘要、关键帧 | 6 分钟素材出可引用摘要 | 1–2 周 | 中（看质量） |
| **M3** | 口播闭环 | 5 个 Skill + 工具集 | 真实素材出成片+工程+报告 | 2–3 周 | 高（审片） |
| **M4** | 工作台只读 | 路由 + catalog + iframe 页面 | 浏览/播放/“做同款” | 3–5 天 | 低 |
| **M5** | 工作台交互 | 时间线、字幕、选中、版本 | 人改→AI 改→不覆盖 | 2–3 周 | 高（体验） |
| **M6** | 独立端 | 桌面壳或独立入口 | 双击启动、独立窗口 | 2–4 周 | 中 |

累计到“Agent 可演示”约 6–9 周；到“有工作台的独立端”约 3–4 个月。**这个估算是排期假设，不是承诺**，M2 的转写质量是最大变量。

## 5. 各阶段详述

### M0 决策钉子（3–5 天）

**做什么**：把四个会决定后续所有代码的选择写成一页纸的决定，并写一个 spike 证明可行。

**不做什么**：不选编辑器（OpenChatCut/FableCut/Timeline 推迟到 M5 再评估）、不搭 UI、不写 Skill。

| ADR | 决定 | 推荐 | 复审条件 |
|---|---|---|---|
| ADR-001 | 项目模型 | 自研薄 JSON，字段对齐 OTIO 概念，不引依赖 | M5 需要导出到外部编辑器时复审 |
| ADR-002 | 渲染路线 | ffmpeg 起步（剪切/拼接/字幕/混音） | 需要动效/多轨关键帧时复审 |
| ADR-003 | 中文转写 | FunASR 优先，WhisperX 备选 | 产品名/数字/否定词错误率 > 5% 时换 |
| ADR-004 | DSH 版本 | 锁定 0.2.1 系列并记录 commit | 上游破坏性变更时复审 |

**Spike 验收**（不接模型）：
```bash
node spike.mjs --input sample.mp4
# 依次输出：probe 结果、假转写 JSON、硬编码选段、拼接后的 out.mp4、回读校验报告
```
通过标准：out.mp4 能播放、时长误差 < 1 帧、报告字段齐全。

---

### M1 无头内核（2–3 周）

**范围**：`project` / `commands` / `versions` / `jobs` / `ffmpeg 适配器` / `CLI`。
**不做**：不接 LLM、不做 UI、不做转写（M2）、不做多轨/转场/变速。

| 卡号 | 任务 | 产出 | 验收命令/标准 | 预估 |
|---|---|---|---|---|
| M1-T1 | 工程 schema | `schema/project.schema.json` | 用 schema 校验手写样例通过 | 0.5 天 |
| M1-T2 | 时间基准 | `time.ts`：帧/微秒/ timecode 互转 | 250 组随机值往返无损 | 0.5 天 |
| M1-T3 | 编辑命令 | `apply(cmd, baseVersion)` + 幂等 | 同命令提交两次，version 只 +1 | 1.5 天 |
| M1-T4 | 版本与撤销 | 版本链 + `revert` + 产物缓存 | 回到 v1 不触发重渲染 | 1 天 |
| M1-T5 | 媒体探测 | `probe(path)` 归一化输出 | 5 种格式（mp4/mov/mkv/webm/m4a）正确 | 1 天 |
| M1-T6 | 渲染执行 | `render(project, version)` | 输出可解码，时长误差 < 1 帧 | 2 天 |
| M1-T7 | 任务运行器 | job 状态机 + 进度 + 取消 | kill 后状态可解释、可重试 | 1.5 天 |
| M1-T8 | 产物回读 | `verify(artifact, project)` | 逐项比对并出 JSON 报告 | 1 天 |
| M1-T9 | CLI | `vcut probe/plan/apply/render/check` | 一条命令跑完 demo 工程 | 1 天 |

**M1 退出条件**（三条全过才算完）：
1. `vcut apply` 改一版 → `vcut revert` 回滚 → 再改一版，`project.json` 始终可重开；
2. 同一命令重复提交不产生重复版本；
3. 渲染前后 `verify` 报告一致（除预期差异）。

### M2 素材理解（1–2 周）

| 卡号 | 任务 | 产出 | 验收 |
|---|---|---|---|
| M2-T1 | ASR 适配器 | `transcribe(path) → {segments[], words[]}` | 10 分钟中文音频，词级时间齐全 |
| M2-T2 | 转写质量表 | 20 条真实样例的错误清单 | 产品名/数字/否定词单独统计 |
| M2-T3 | 素材摘要 | `summarize(asset) → {topics, quotes, gaps}` | 摘要每条都能回溯到时间码 |
| M2-T4 | 关键帧/短预览 | `frames(asset, t)` | 抽帧可被 UI 直接引用 |
| M2-T5 | 上下文策略 | “摘要 + 检索”替代全文注入 | 6 分钟素材的上下文 < 8k token |

**不做**：OCR、视觉理解、说话人分离（留给后续批次）。

### M3 口播闭环（2–3 周）

**范围**：5 个 Skill（主 Skill + footage-intake + revise-edit + render-qa + talking-head-roughcut）+ 7 个工具。

| 卡号 | 任务 | 要点 | 验收 |
|---|---|---|---|
| M3-T1 | `video-editing` 主 Skill | 只写选择与组合规则 | 能在 3 个不同任务里正确挑 Skill |
| M3-T2 | `footage-intake` | 检查→转写→按需看画面→摘要 | 摘要含来源时间与不确定项 |
| M3-T3 | `talking-head-roughcut` | 语义选段、去重复停顿、保完整句 | 输出**提案**，不直接改工程 |
| M3-T4 | `revise-edit` | 把“开头再短五秒”落到片段 | 改动范围可枚举、带基准版本 |
| M3-T5 | `render-qa` | 文件/内容/人工审片三分 | 报告三类不混 |
| M3-T6 | 工具集 | probe/transcribe/propose/apply/render/check/read | 工具名与参数在 schema 内 |
| M3-T7 | 端到端 demo | 一段真实口播 → 成片 | 成片 + 工程 + 报告齐全 |

**M3 退出条件**：文档 5.3 的七条验收里，前六条在真实素材上跑通；第七条（输出可播放、工程可重开）由 M1 保证。

### M4 工作台只读（3–5 天）

照归藏插件的结构做，不要发明新架构：

| 卡号 | 任务 | 产出 |
|---|---|---|
| M4-T1 | host 路由 | `/video-studio/`、`/api/catalog`、`/works/…` |
| M4-T2 | 页面 | `gallery/`：作品库 + 播放器 + 只读时间线 |
| M4-T3 | 挂载 | `client.js`：`sidebar.panellist` 图标 + `main` slot 的 iframe |

**验收**：不改 host 内核，只加文件；页面能列出 M3 的成片并播放；点“做同款”能开新会话且草稿正确。

### M5 工作台交互（2–3 周）

| 卡号 | 任务 | 验收 |
|---|---|---|
| M5-T1 | 播放器与时间线同步 | 拖动、跳转、帧级定位 |
| M5-T2 | 字幕编辑 | 改字幕后保存为新 version |
| M5-T3 | 选中对象 → 提修改 | 生成带对象引用的 command |
| M5-T4 | 版本对比 | 两个 version 的 diff 可见 |

**验收**：用户手改字幕后，Agent 继续修改仍保留该修改（文档 5.3 第二条）。

### M6 独立端（2–4 周）

| 方案 | 成本 | 建议 |
|---|---|---|
| DSH Desktop 打包 | 2–4 周 | **首选**，插件直接跑在桌面壳 |
| 独立 Web 入口（端口 + 反代 + 登录） | 1–2 周 | 需要多端访问时 |

## 6. AI 协作规范（本项目最重要的部分）

### 6.1 角色边界

| 角色 | 负责 | 不负责 |
|---|---|---|
| 人 | 方向、契约、验收、审美、风险取舍 | 不写重复代码 |
| AI | 按卡实现、写测试、跑验收命令 | 不擅自改契约、不擅自加依赖、不替人做产品判断 |

### 6.2 任务卡模板（写卡时照抄）

```md
### M?-T? <名称>
- 目标：一句话
- 输入：现有文件/接口
- 输出：新增或修改的文件（精确路径）
- 验收：可执行命令 + 期望输出
- 禁止：不得修改的文件/不得引入的依赖
- 人工检查项：只有人能判断的部分
```

### 6.3 会话卫生

1. **一卡一会话**。做完关闭，不续用旧会话做新卡（避免上下文污染）。
2. 开场必喂：本文件第 3–6 章 + 当前任务卡 + 相关契约文件。
3. 不让 AI 一次改超过 3 个文件；跨模块重构单独开卡。
4. AI 说“完成”后，先跑验收命令，再让人看 diff。

### 6.4 红线（AI 不得自行决定）

| 红线 | 说明 |
|---|---|
| `project.schema.json` | 字段增删必须人批准 |
| 命令语义（apply/revert/diff） | 语义变化必须人批准 |
| 错误码表 | 新增错误码必须人批准 |
| 时间基准 | 帧/微秒规则不得改 |
| 新依赖 | 任何 runtime 依赖引入前必须批准 |
| 目录结构 | 不得把内核代码放进 DSH 插件目录 |

### 6.5 证据制验收

每个任务卡完成后必须附：
- 验收命令的完整输出（不是“应该能过”）；
- 产物路径（文件真实存在，能被第二次打开）；
- 改动的文件清单。

### 6.6 人工审查清单（10 条）

1. 是否偷偷改了契约？
2. 是否只跑了 happy path？
3. 是否有 `try/catch` 吞掉错误？
4. 是否把确定性逻辑写进了 prompt？
5. 是否新增了未批准的依赖？
6. 是否把状态放进了会话上下文而非工程文件？
7. 时间码是否混用了秒/帧/微秒？
8. 错误信息是否可解释（能否据此重试）？
9. 是否留下不可复现的产物（路径写死、临时目录）？
10. 测试是否验证行为而非实现？

### 6.7 AI 卡住时的退回顺序

`跑验收 → 读错误 → 缩小到单测 → 换实现 → 报告卡点`。连续两轮无进展就停下写报告，不许“再试一次”。

## 8. 契约规格（给 AI 实现的粒度）

### 8.1 project.json 核心字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schemaVersion` | int | 是 | 从 1 开始 |
| `projectId` | string | 是 | 稳定 ID |
| `fps` | number | 是 | 项目帧率 |
| `assets[]` | array | 是 | `{id, path, durationUs, width, height, fps, tracks}` |
| `tracks[]` | array | 是 | `{id, kind: video/audio/subtitle, segments[]}` |
| `segments[]` | array | 是 | `{id, assetId, srcInUs, srcOutUs, outStartFrame, speed}` |
| `subtitles[]` | array | 否 | `{id, text, inFrame, outFrame, style}` |
| `requirements` | object | 否 | 目标时长、画幅、受众、必须保留项 |
| `versions[]` | array | 是 | `{version, parent, commandId, createdAt}` |

规则：素材只读；所有修改产生新 `version`；`segments.id` 一旦生成永不复用。

### 8.2 command 结构

```json
{
  "commandId": "uuid",
  "baseVersion": 3,
  "op": "trim|reorder|delete|setSubtitle|setStyle|...",
  "target": { "trackId": "t1", "segmentId": "s7" },
  "params": {},
  "actor": "agent|user"
}
```

返回 `{ ok, version, diff }` 或 `{ ok: false, code }`。

### 8.3 job 状态机

`queued → running → succeeded | failed | canceled`

- 必须有 `progress {stage, percent}`；
- 失败保留 `stderrTail` 与重试次数；
- 取消要能真正杀掉子进程；
- 重启后按产物核对，而不是信状态文件。

## 9. 能力适配器规范

| 项 | 约定 |
|---|---|
| 签名 | `run(input, {signal, onProgress}) → Promise<result>` |
| 超时 | 每适配器声明默认超时 |
| 取消 | 必须响应 `signal`，杀进程组 |
| 错误 | 归一化为 `{code, message, retryable}` |
| 缓存 | 以输入 hash + 参数为键 |
| 产物 | 落到 `projects/<id>/artifacts/`，不写临时目录 |

## 11. 度量与验收

- **任务集**：12–20 个明确剪辑任务，先少后多；留 3 个不参与调优做回归。
- **指标**：完成率、关键内容保留率、人工修改次数、耗时、成本、失败原因分类。
- **节奏**：每周一次小回归，每阶段一次完整回归。
- **失败也要记录**：失败比成功更能说明瓶颈。
