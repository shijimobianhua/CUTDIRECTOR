## 1 执行原则与阅读方式

### 1.1 最合适的开发组织

采用“同一真实任务，工作台、Agent、Skill、服务和工具共同迭代”的方式。先约定可检查的输入输出，做最小可用方法与工具，在真实任务中发现缺口，再一起修订，最后稳定发布。

Skill 不必等到全部代码完成才写，也不宜在工具和素材未验证时写成大而全的方法库。M0 做场景、契约与功能骨架；M1 实现主 Skill 和局部修改的最小版本；M2 随真实分析与导出补齐五个方法；M3 做选择、组合、失败与回归验收。

Agent 的运行复用 DSH；Agent 的产品行为由入口指令、按需 Skill、工具结果、当前工程和任务状态共同形成。Skill 是方法文本，不能代替代码强制执行版本、事务、文件和任务约束。

### 1.2 文件之间如何分工

| 文件或记录 | 负责内容 |
| --- | --- |
| PRD | 用户、范围、产品行为、优先级、FR 与验收目标 |
| 本手册 | 架构、逻辑契约、Skill 制作、开发次序、任务卡、验证与接入办法 |
| 总览 v2 | 总体索引与 AC-01 至 AC-10 原始基线 |
| ADR | 对未决技术事项给出选项、证据、决定、后果与复审条件 |
| 实际任务卡与交接 | 当前完成情况、真实命令、文件、证据、未解问题 |
| 运行与评测记录 | 本次所用版本、输入、结果、失败和人工审片意见 |

旧设计草案属于历史输入，其中固定六工具、最后写 Skill、先内核后工作台的顺序不沿用。用户最新明确要求优先；技术测试用于修正假设，不能偷偷缩小产品目标。

### 1.3 实施状态必须区分

设计提出 → 接口存在 → 适配能调用 → 集成真实可用 → 固定任务通过 → 人工接受，是不同状态。只运行过硬编码选段或假转写，不能报告 Agent 已具有内容剪辑能力。

本文不指定未经确认的安装命令、脚本名或工期。M0 建立真实运行说明后，任务卡只填写仓库中实际存在并运行过的命令。

## 2 总体架构与工程所有权

~~~text
用户需求 / 选中对象
       │
       ├─ 工作台 ──────────────┐
       │                      │
       └─ DSH 中的视频 Agent  │
             │                │
        主 Skill 按需协调      │
        通用流程 / 专项方法    │
             │                │
        视频工具适配 ─────────┤
                              ↓
                 项目服务与唯一编辑入口
                命令 / 版本 / 历史 / 变化事件
                              │
                编辑器、存储和能力适配器
                媒体 / ASR / 画面 / 渲染等
                              │
               分析、业务任务、日志、真实产物
~~~

### 2.1 唯一权威工程

M0 比较主编辑路线，M1 再固化 schema 映射。采用现成编辑器时，原生工程和原生编辑服务可以拥有时间线，产品服务负责共同入口、映射与业务记录；自研薄层时由自己的命令服务拥有。

不能在原生编辑器之外再维护一份可以独立修改的权威 project.json。镜像、索引和分析清单可以存在，但须注明来源与 revision，不能直接用镜像覆盖新工程。

人工编辑也要进入同一历史与变更通知。若候选引擎允许 UI 私自写状态、无法观测或校验，则补齐入口后再验收；定时复制文件不算解决共同编辑。

### 2.2 模块依赖

| 层 | 职责 | 可依赖 |
| --- | --- | --- |
| core | 项目逻辑、时间、提案、命令约束、版本、业务任务与接口 | 通用库和抽象接口，不能依赖 DSH 或 React |
| adapters | 原生编辑器、媒体、转写、渲染、持久化实现 | core 与具体后端 |
| dsh | 插件装载、工具、会话上下文、运行任务和 Host 通信 | core、adapters 和锁定版本的 DSH |
| client | 页面、播放、选择、字幕、片段与状态展示 | Client API、业务视图模型和所选编辑组件 |
| skills | 路由、工作方法、检查与失败处理 | 已发布的业务工具契约与可按需读取的参考 |

core 可以与插件同包，禁止的是反向依赖。工具接线与 Client 接线都可以使用 DSH API，不要求所有接触框架的代码挤进一个入口文件。

### 2.3 不另外建设的系统

复用 DSH 的模型、会话、工具、Skill、插件组合、凭据与界面扩展。产品增加视频业务能力目录、项目服务和持久化任务，不另建通用 Agent 框架、通用插件市场或独立会话系统。

## 3 M0 选型方法与目录建议

### 3.1 主编辑底座比较

先从 OpenChatCut、FableCut、Timeline Studio 中筛选，最多让两条路线进入实际小样；必要时将自研薄层作为比较选项。不是同时整合三套完整应用。

| 比较维度 | 必须拿到的证据 |
| --- | --- |
| 共同读写 | 真实 Agent 和真实页面读取同一工程；人工纠正后 Agent 接续 |
| 事务与版本 | 能控制全部写入口，旧基准拒绝、重复操作不重复应用 |
| 工程能力 | 字幕、片段、基础声音、重开、稳定对象与历史映射 |
| 预览与导出 | 相同项目子集下画面、字幕、音画对应，真实成片可解码 |
| DSH 接入 | 页面装载、Host 通信、模型工具调用、异步进度和取消 |
| 运行条件 | Windows、依赖安装、字体、模型、CPU/GPU/内存与实际耗时 |
| 复用条件 | 选定版本的源码、依赖和分发条件，维护与改造成本 |

如果原生引擎无法提供所需原子性，不能只在外层增加 revision 就宣称事务成立。应验证可控的单写服务、原生事务或原子文件提交；仍不成立时记录缺口并复审底座。

### 3.2 建议的源码布局

~~~text

│  ├─ core/               项目、时间、命令、任务、能力接口
│  ├─ adapters/           编辑器、存储、媒体、ASR、渲染实现
│  ├─ dsh/                Host、工具、任务桥接、页面通信
│  └─ client/             页面、播放、选择、字幕、片段、版本
├─ skills/
│  ├─ video-editing/SKILL.md
│  ├─ footage-intake/SKILL.md
│  ├─ revise-edit/SKILL.md
│  ├─ render-qa/SKILL.md
│  └─ talking-head-roughcut/SKILL.md
├─ contracts/             M0/M1 形成的 schema、样例和错误语义
├─ test/                  行为、集成、媒体与 Agent 任务
├─ docs/adr/              决策与证据
├─ docs/tasks/            实际执行任务卡与交接
~~~

以上是建议路径，当前不表示文件存在。发布产物如何打包、是否 TypeScript、构建工具和存储选型，在 M0 记录；不先用目录锁死编辑引擎。

五个 Skill 在可发现根下采用平级目录，职责分类写在目录清单或文档中。不要因为“主—通用—专项”的概念层级，做成需要递归发现的多层目录。

### 3.3 项目数据布局

配置的项目工作区至少分离：工程或原生工程引用、当前头与历史、原素材引用、工作媒体、分析产物、任务与尝试、日志、中间文件、发布成片与字幕、反馈。

原素材只读。工作媒体与缓存可以重建；仍被工程或产物清单引用的数据不自动删除。工程使用外部文件引用还是副本、路径重定位与项目迁移，在 ADR-005 决定。DSH 配置目录可保存设置和索引，不要求把所有大媒体放入配置目录。

## 4 核心逻辑契约

这些是需要实现的逻辑约束，不是已经固定的原生文件格式。先映射选定底座，再为真正需要的字段定义 schema、正例、反例与升级方式。

### 4.1 对象与标识

| 对象 | 必须表达 |
| --- | --- |
| ProjectHead | projectId、schemaVersion、currentRevision、outputSpec、requirements、原生工程引用 |
| Asset | assetId、内容 hash、路径/URI、来源、媒体流规格与原始时间基准 |
| WorkingMedia | 自身标识/hash、原 assetId、转换配置、时间原点与映射 |
| Segment | 不复用的 segmentId、trackId、assetId、来源区间、成片位置 |
| Track | 持有片段引用及轨道配置，片段实体只保存一份 |
| Transcript | 原识别文本、来源词/区间、时间精度、缺失与不确定项、实现版本 |
| Caption | 纠正记录与字幕实例；实例关联 segmentId 和来源词/区间，派生成片时间 |
| Revision | revision、父版本、命令、操作者、差异、不可变内容或原生等价历史 |
| Artifact | 类型、输入摘要、生产者/版本、状态、位置、hash 与来源/版本引用 |
| Feedback | 项目、revision、请求、实际差异、接受/否决/修正、长期偏好是否确认 |

同一素材多次出现产生不同片段实例。字幕纠正不能只以成片秒数为唯一键；排序后仍能追到相应片段。独立标题明确采用成片时间或其他受支持锚点。

### 4.2 时间与媒体

项目时间采用整数帧、有理数 fps 和半开区间 [in, out)。源时间保留媒体 time base、原始时间戳与原点；微秒可作接口表达，不能替代所有原始信息。

点位默认取最近帧并统一半帧处理；需要覆盖来源完整内容的区间起点向下、终点向上，记录采用策略。30000/1001 不能用小数 29.97 替代精确计算。

VFR 或不兼容素材可以转成 CFR 工作媒体，但必须保存原素材、转换参数、旋转/像素比例、时间原点和音画偏移的处理记录。转写、抽帧、字幕和渲染明确使用哪份媒体；归一化后不假设源与工作媒体时间天然相同。

首版 speed 固定为 1，变速、转场和多机位另扩展映射。视频帧数、音频采样与编码延迟分别验收，不统一套用“一帧误差”覆盖全部情况。

### 4.3 统一编辑提案

~~~json
{
  "proposalId": "proposal-example",
  "projectId": "project-example",
  "baseRevision": 12,
  "scope": {"segmentIds": ["seg-a"], "captionIds": []},
  "constraintsRef": "requirements-example",
  "operations": [],
  "evidenceRefs": [],
  "protectedRefs": [],
  "unresolved": []
}
~~~

这是说明结构的示例，空 operations 不构成可执行剪辑方案。实际操作联合类型、时间字段、schema 与验证器在选型后定义。

分析类 Skill 产出简报或观察；编辑类方法形成以上共同提案。自然语言说明和提案分别存储，工程不能直接从一段解释文本执行。

validateProposal 检查结构、对象、时间、所需能力、保护范围和当前基准，返回可解释问题或可应用的规范化提案。语义保留的判断需证据与内容检查，不能声称 JSON 校验已经证明“意思没变”。

### 4.4 命令提交与历史

逻辑命令包含 commandId、projectId、baseRevision、操作或操作批次、目标、参数与作用范围。批次的应用结果必须明确采用全有或全无；原生后端不支持时先解决提交策略，不返回含糊的部分成功。

处理顺序：校验调用者与请求 → 检查已记录的幂等结果 → 校验基准和约束 → 原子提交状态、历史与幂等结果 → 发布对应 revision 的变化通知。

同 ID 同内容返回原成功结果；同 ID 不同内容报冲突。已成功结果可以早于当前头，调用者随后读取 currentRevision。旧基准失败后重新理解形成新命令，不能修改 payload 却沿用旧 commandId。

语义相同请求的规范化摘要规则必须固定。原子提交内部保证两个调用不能都用同一旧基准成功覆盖。单用户也可能同时有页面、Agent 和任务回写，不能省略竞争验证。

revision 单调递增、不复用。r3 恢复 r1 的内容后生成 r4，保留历史；撤销与恢复可用原生机制，但业务与原生历史的对应关系必须可追踪。

### 4.5 变化事件与一致读取

事件至少携带项目、newRevision、受影响对象和命令关联；事件发生在持久化提交后。工作台重连先读项目头，再恢复订阅或补取差异，发现缺口时重新读取权威状态。

选中对象和播放位置属于交互状态；内容属于工程事实。对象删除或拆分后使旧选择失效或显式重映射，不能把“第一个片段”永久当作同一对象。

## 5 工具、能力与适配器

### 5.1 Agent 可见的逻辑工具面

以下名称表达职责，实际命名按锁定 DSH 版本和实现确定。不要求每个逻辑动作一个工具，也不把所有动作合成无法定位失败的万能工具。

| 逻辑工具组 | 主要职责与结果 |
| --- | --- |
| project read | 读项目头、当前内容、要求、变化和历史；支持按范围读取 |
| media intake | 导入、探测、规范化，返回 assetId 和媒体信息 |
| analysis submit/read | 转写或其他分析，返回 job/artifact 引用与可回查摘要 |
| media inspect | 读取来源/成片帧、短片段、转写范围，明确坐标和来源 |
| capability list | 返回能力与就绪状态；与 Skill 目录分开 |
| proposal validate/apply | 校验提案，经共享命令入口提交，返回 revision、diff 和 affectedIds |
| history restore | 查询与恢复，生成新版本 |
| render submit | 固定清单，返回业务任务与所属版本 |
| job control | 查询、有限等待、取消、显式重试，返回有依据的状态 |
| artifact verify/read | 真实探测、内容证据和范围读取，不把完整日志塞给模型 |
| feedback record | 保存项目修正或明确确认的偏好，不自动推广到长期 |

最初 build_edl 的思路归入提案校验与保存：模型负责内容选择，工具检查并落实。工具不能内部无依据地用固定时间段冒充 Agent 选段。

### 5.2 统一结果与错误

成功返回结构化结果、数据或产物引用及相关项目/版本；长任务返回任务引用，不只返回无归属路径。错误至少含 code、message、retryable、detailsRef 及必要上下文。

建议区分 VALIDATION_ERROR、REVISION_CONFLICT、SCOPE_VIOLATION、CAPABILITY_UNAVAILABLE、MEDIA_MISSING、UNSUPPORTED_MEDIA、EXECUTION_FAILED、CANCEL_PENDING、NEEDS_RECONCILE 等语义。名称待实现固定，常规兼容新增不必逐个打断开发。

原始日志落盘，摘要返回模型；read_artifact 以类型、范围和大小读取。模型不得读取凭据原文，也不能用日志中的内容生成未经约束的 shell 操作。

### 5.3 能力提供方契约

| 字段或行为 | 要求 |
| --- | --- |
| 身份与版本 | providerId、capabilityId、apiVersion、implementationVersion |
| 输入输出 | 类型化 schema、时间单位、产物类型和正反例 |
| 就绪 | available、notConfigured、missingDependency、incompatible、temporarilyUnavailable 等及原因 |
| 限制 | 语言、格式、精度、资源、执行位置、支持操作与效果 |
| 调用 | run(input, context)，context 含取消信号、进度和执行身份 |
| 进度 | stage 必有，percent 可未知 |
| 取消 | 任务级、进程级、尽力取消或不支持，按实际能力声明 |
| 缓存 | 内容输入、参数、模型/工具/适配器版本决定有效性 |
| 结果 | 原始结果引用、规范化数据、缺失与不确定字段 |

中文 ASR 可以内部选 FunASR 或其他实现，不必让每家供应商都成为独立模型工具。换实现时用相同素材检验关键字、数字、否定、时间单位、覆盖与缺失，不只确认 HTTP 200。

### 5.4 接入外部项目的固定流程

明确能提供的能力和非能力 → 固定版本和依赖 → 在隔离环境跑真实样例 → 转换统一输入输出 → 接业务任务与产物 → 接就绪状态 → 做失败/取消/重复提交测试 → 加相应 Skill 方法与工作台回查 → 发布支持范围。

Python、CLI、HTTP、MCP 都是实现载体。Python 重依赖可独立环境或服务运行，不将所有模型塞进 DSH 主进程。MCP 发现到工具不代表异步恢复和取消已自动解决。

安装、启用、依赖就绪和任务成功分别记录。卸载或更换 provider 前处理在途任务并保留旧结果的生产者记录。

### 5.5 其他 DSH 插件怎样提供能力

建议在产品插件侧定义视频能力注册服务，其他插件作为 provider，Agent 工具与页面作为 consumer。这是业务服务设计，具体 Cordis 服务定义与注入语法按 M0 版本实施，不假定 DSH 自带名为 videoCapabilities 的现成服务。

provider 加载时注册描述、schema、实现和就绪检查，卸载时注销并处理在途任务；consumer 按 capabilityId 与 API 兼容范围解析实现。目录同时考虑当前 scope、配置与资源，不能把其他会话或未启用范围的能力直接暴露出来。

对于只有 CLI/HTTP/MCP 的开源工具，可增加薄适配插件注册相同能力；原项目本身不必变成 DSH 应用。原始分析结果归一化为 artifact，生成素材通过正常入库；编辑操作仍提交共同项目服务。provider 不另外拥有一份时间线，也不直接覆盖权威工程。

新增 provider 不一定需要新页面。先复用素材、分析、任务和产物展示，确有特殊交互再扩展面板。发布能力与发布专项 Skill 可以分包，但必须记录兼容与就绪关系，不能只装方法就显示“功能可用”。

## 6 渲染、业务任务与恢复

### 6.1 冻结渲染输入

renderManifest 至少包含 projectId、revision、工程快照及 hash、所有渲染相关媒体/字幕/字体等依赖 hash、输出规格、参数与实现版本。生成后不可变，任务与产物引用该清单。

render(manifest) 与 verify(artifact, manifest) 使用同一输入。导出期间新编辑只产生新 revision，不修改旧 manifest；旧结果只标记其实际版本。

缓存键取渲染相关内容、实现与参数，不只取 revision，也不因无关时间戳失效。复用前验证产物存在、完整、hash 和适用条件；恢复旧内容可命中缓存，但不能保证永远不用重渲染。

工作文件或 .partial 可以存在；完成必要校验后发布稳定产物。不能仅因路径存在、进程退出码为零或任务状态 completed 就登记为成功作品。

### 6.2 三层任务身份

| 层次 | 保存内容 |
| --- | --- |
| businessJob | 持久化业务 jobId、requestId 与输入摘要、项目/版本/清单、状态、尝试与结果 |
| executionAttempt | attemptId、执行器、启动与结算、runtimeJobId/外部任务号、日志和退出证据 |
| DSH runtime job | 当前运行的 owner Session、进度、输出和停止控制，按锁定版本使用 |

业务状态使用 queued、running、verifying、succeeded、failed、canceled；另记录 cancelRequested、needsReconcile、interrupted 等恢复事实，不将它们混成互相矛盾的多个终态。

DSH completed 对应执行结束，业务进入 verifying；通过检查才 succeeded。stopping 只表示停止处理中；killed/failed 要核对实际资源和产物。Session turn 结束不代表所有异步工作结束。

### 6.3 重复提交、重试与执行权

调用端每个逻辑请求生成稳定 requestId，网络重试沿用；服务以 requestId 和规范化输入摘要原子去重。同 ID 不同输入拒绝，同内容返回原 businessJobId。

每个 job 最多一个未结算 attempt。启动、恢复与显式重试原子取得执行权；执行结果不明先核对，不重复发起。失败后的显式重试创建新 attempt，重试请求本身也做幂等。

只读分析/渲染重试不重复修改工程。自动修正若需编辑则生成新的可追溯提案与命令，不能藏在渲染重试中。

### 6.4 取消与重启核对

取消请求先记录，再由适配器执行；本地进程核对属于本 attempt 的进程树，外部服务使用其任务级能力。共享服务只能中断当前任务时，不得假装可以安全取消任意排队任务。

重启后读取业务记录、manifest、已发布产物与外部状态，判断已完成、已失败、已停止还是仍不明确。仍不明确时保持待核对并提供证据。允许从有效输入重新执行，不承诺任意后端断点续跑。

DSH 运行时状态、Session 持久化生命周期与业务持久化各有用途。参考[官方 Jobs 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/jobs.md)，实施须核对精确版本，尤其 owner、结束记录和资源释放含义。

## 7 产品 Agent 的开发方法

### 7.1 入口配置保持薄

建立视频专用 preset 或等价的 DSH 组合，包含模型、视频工具、Skill 目录、项目上下文与必要通用能力。默认工具集服务当前范围；搜索、生成等按能力扩展，不受旧草案固定工具数限制。

入口只规定角色、事实来源、主 Skill 入口、作用范围、工具结果与完成标准、失败交接规则。视频任务开始或恢复时引导加载 video-editing；只提供文件名不能保证模型必然读取。M0/M1 用真实轨迹验证入口能生效。

长期不变的执行约束由代码保证。给模型通用文件工具时，不允许绕过项目服务直接覆盖权威工程；终端和脚本参数限定业务范围，不能让 Skill 各自自由拼接任意写工程命令。

### 7.2 上下文构成

| 内容 | 提供方式 |
| --- | --- |
| 当前现场 | projectId、currentRevision、选择、任务简报、保护项和能力摘要 |
| 当前方法 | 已选择的 Skill 及其实际版本/hash，按需加载正文 |
| 内容证据 | 素材和分析摘要、来源区间、按需转写/帧/短预览 |
| 运行事实 | 业务任务和产物引用、结构化错误、必要日志片段 |
| 持久化要求 | 工程、任务与反馈读取自服务，不从聊天记忆推测 |

对话可能压缩，执行前仍读最新项目。大转写分页或按段检索，摘要保留回查引用；不能为了降低 token 删除关键限制和不确定项。

### 7.3 标准运行闭环

确定当前请求与版本 → 按需读方法与能力 → 补充证据 → 形成提案 → 校验并应用 → 检查受影响结果 → 需要时局部修正 → 交付或说明待决问题。

方法选择、提案校验和真正应用分开记录。Agent 对任务状态的口头总结不改变业务状态。转写、参考文字和外部工具文本均作为数据处理，不能覆盖产品入口或用户约束。

### 7.4 恢复与修正

恢复会话先读取工程头、进行中任务和最近相关反馈，不直接重放聊天中的写操作。修正循环记录目标、证据、提案、结果与次数；上限按配置与实测设定，超出给可用版本和明确缺口。

内容、自然度和关键语义是 Agent 与人工验收责任；版本、时间边界、幂等与原子性是服务责任。发现误删产品名时先确定识别、对齐、方法、映射还是渲染哪一层有错，再修改对应层。

## 8 Skill 怎样制作、什么时候制作

### 8.1 Skill 与代码的放置判断

| 问题 | 放在哪里 | 原因 |
| --- | --- | --- |
| 怎样组织开头、如何处理重复观点 | 专项 Skill | 依赖内容和创作判断 |
| 什么时候读取画面、何时指出素材缺口 | 通用或专项 Skill | 方法可随任务经验调整 |
| 何时组合方法、发生范围冲突怎样取舍 | 主 Skill | 属于通用协调 |
| 时间换算、版本校验、路径和原子提交 | core / 服务 / 工具 | 必须可强制、可复现验证 |
| FFmpeg 参数、模型调用和输出解析 | 能力适配器 | 隔离运行差异与依赖 |
| 取消、幂等、状态转换和缓存 | 业务任务与执行器 | 提示词无法提供可靠保证 |
| 一次任务目标、片段清单与用户要求 | 工程 / 任务数据 | 不能写死进长期方法 |
| 用户确认的长期字幕偏好 | 偏好记录 | 数据可编辑覆盖，不能为每人复制 Skill |

Skill 可以引用工具步骤、样例或确定性辅助脚本。“方法用文字、执行用代码”不意味着正文不能提操作；含义是正文不替代业务实现和强制约束。脚本调用仍经过相同契约，不能成为第二写入口。

### 8.2 开发时点与成熟度矩阵

| 阶段 | 主 video-editing | footage-intake | revise-edit | render-qa | talking-head-roughcut |
| --- | --- | --- | --- | --- | --- |
| M0 | 定职责、触发、调用关系和完成条件 | 定输入/摘要/缺口 | 定选择与保护契约 | 定检查层次和产物输入 | 定真实选段案例和输出提案 |
| M1 | 最小正文，真实入口可加载 | 有素材检查就联调对应部分 | 最小正文，与人工接续编辑一起验证 | 有真实预览/导出就联调初步检查 | 保留方法草案，不把夹具选段计为能力 |
| M2 | 随真实任务补路由、冲突与交付 | 随探测、ASR、画面完善 | 补来源、字幕重排和多轮局部反馈 | 随真实 manifest、产物和检查完善 | 使用真实转写编写、运行、审片与修正 |
| M3 | 稳定目录、选择、组合与失败处理 | 固定样例回归 | 保护范围与冲突回归 | 文件/内容/人工项联合回归 | 内容与切点、保留任务回归 |

成熟度使用“规划、草案、可加载、端到端验证、发布”标记。M3 发布的是前期已开发的方法，不能把所有 Skill 正文留到 M3 集中补齐。

### 8.3 每个 Skill 的七步制作流程

1. 写场景卡。明确真实任务、使用和不使用条件、输入、输出、成功与失败案例；先确定它是否确实需要独立方法。
2. 人工跑一条参考流程。观察需要哪些内容与工具，记录判断点。手工选段可帮助理解方法，但不能计作 Agent 验收。
3. 定最小契约。说明项目/素材/版本、能力、范围、证据、输出类型和缺口处理；与工具开发一起修订。
4. 写最小正文。包含触发、输入检查、关键判断、工具衔接、失败/冲突处理、输出与验收。不写还没有实现的工具调用承诺。
5. 注册并验证加载。确认目录、作用域、真实 skill 工具、同名来源与资源引用；让 Agent 在对应任务中实际读取。
6. 跑任务并定位失败。看方法选择、证据、提案、实际编辑与产物，区分 Skill 问题和下层错误。
7. 回归和发布。重跑失败样例与受影响保留任务，记录正文版本/hash、契约、依赖、结果与回退包。

一次只针对有证据的问题修改必要规则。不能靠向主 Skill 不断追加补丁覆盖所有专项，也不能将每次偶然错误直接升级为永久通用规则。

### 8.4 正文内容结构

这里只给写作结构，不在本轮创建正式 Skill 包。

| 内容 | 要回答的问题 |
| --- | --- |
| 名称与 description | Agent 什么时候应该选择它？与相近方法有什么边界？ |
| 适用与不适用 | 哪类素材和目标有效，哪些情况应交给其他方法？ |
| 前置输入 | 需要哪些项目、版本、分析、能力与选择信息？ |
| 工作步骤 | 先核对什么，怎样判断，何时补证据，何时执行？ |
| 保护与冲突 | 哪些内容不可破坏，目标互相冲突怎样处理？ |
| 工具与产物 | 调用已发布的哪类工具，结果如何引用，输出什么类型？ |
| 失败与交接 | 配置、素材、时间精度、旧基准不足时怎样推进？ |
| 验收与示例 | 方法何时完成，哪些真实样例证明，哪些仍需人工判断？ |

description 应包含可区分的任务意图，不写成“处理所有视频”的重复描述。大参考、特例与样例按需读取，正文保留最重要的判断；不设未经实测的固定 token 上限。

### 8.5 DSH 中的发现与加载

本轮查阅的[官方 Skills 文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md)提供 Skill 目录与正文按需加载机制。模型通常先看到名称与描述，再调用 skill({name}) 读取正文；项目不能假设五份正文会自动全部注入。

当前文档支持目录包 name/SKILL.md 或平级 Markdown，明确不递归发现任意多层 SKILL.md。源码中的 skills/ 必须通过所选版本支持的 bundled/custom 根或专门 provider 接入；仅把目录放进 npm 包并不等于 DSH 已发现。

M0/M1 验证下列接线：启用对应 Skill 能力与模型侧消费者 → 注册发布目录或 provider → 查询当前 scope/cwd 可见目录 → 加载主 Skill → 再按需加载专项 → 检查实际正文与资源位置。

可以先用明确配置的根做开发验证，再按插件发布要求注册包内资源。具体 API、配置键、调用权限与 Client 行为以 ADR-004 锁定版本为准，不直接照搬最新分支示例。

同名 Skill 可能由项目、用户或其他 scope 覆盖。诊断页或日志应能查到实际来源、正文 hash 与作用域；模型只需简洁路由摘要。目录暂时不完整不能直接解释为“绝不存在该 Skill”。

主、通用、专项是业务分类，DSH 不会因为目录名字自动实现层级调用。实际组合由 Agent 在主 Skill 规则下选择，是否需要额外的任务约束由产品服务校验。

### 8.6 产品侧能力清单与门控

Skill 的名称、描述与正文走 DSH 原生机制。所需 capability、业务版本、测试集和产出类型，可使用产品侧 manifest 或等价配置维护；这是我们定义的元数据，不能假称 DSH 自动识别并执行这些字段。

manifest 至少关联 skillName、skillVersion/contentHash、requiresCapabilities、outputType、supportedScope、compatibility、evaluationRefs。Agent 可见精简说明，服务在执行时校验实际能力与范围。

缺少能力时允许读取方法解释限制，但不能执行不可用步骤或绕过约束。只有一个口播专项时，仍需通过夹具验证其他方法可被选择和组合。

### 8.7 首版五个 Skill 分别如何落地

| Skill | 首个实现机会 | 最小可验证功能 | 重点反例 |
| --- | --- | --- | --- |
| video-editing | M1 读项目与提交工具就绪 | 新任务读现场、调用所需方法、处理缺口、组织交付 | 所有任务都走口播；未加载方法就声称使用；能力缺失仍报完成 |
| footage-intake | M1 探测，M2 真实 ASR 与画面 | 识别可用输入、生成引用摘要、报告缺时间或缺音轨 | 静音素材强行口播；全量塞日志；精度不足仍精确切词 |
| revise-edit | M1 人工字幕编辑与命令入口 | 读最新版本，限定目标，保留非目标纠正，显示差异 | 旧基准覆盖；删除后续限制；重排导致字幕纠正错位 |
| render-qa | M1 初步产物，M2 完整清单与检查 | 对应 manifest，检查文件、关键内容和待审片项 | 只看退出码；用 r2 验 r1；字幕出现词就断言原声保留 |
| talking-head-roughcut | M2 真实转写、来源与提案工具 | 根据内容组织选段、重复/停顿处理、语义保留 | 否定词丢失；截断句意；为时长删保留项；照搬示例时间码 |

五个方法都需要真实 Agent 加载和任务证据。Skill 文件格式检查、拼写检查和“文件存在”只能证明可读性，不能证明方法有效。

### 8.8 两个专项怎样组合

先由主流程确定分工与保护范围。涉及相同对象的两份提案不能并行盲目应用。第一份应用后读取新 revision 和目标映射，再重新核对第二份；若内容有冲突则返回协调。

示例：口播方法先整理讲解；第二专项只处理指定 B-roll，不改变受保护讲解音轨与字幕。检查最终提案与 diff，证明专项没有越界。M3 可以用受控测试专项完成接口证明，真实卡点能力需另有节拍、素材和成片验收。

同一项目切换方法时沿用当前工程和已接受编辑。Skill 读取是模型获取指令，不等于程序函数调用；可靠输出依靠业务工具 schema、验证与任务轨迹。

### 8.9 一条功能怎样把 Skill 和代码一起做

以“用户改过产品名字幕后，请 Agent 再缩短开头五秒”为开发样例，按以下顺序交付同一个行为。

| 小步 | 方法侧工作 | 代码与界面侧工作 | 验证 |
| --- | --- | --- | --- |
| 定场景 | revise-edit 草案标出最新版本、目标、保护项与期望提案 | 定义选择上下文、项目读取和提案接口样例 | 双方对同一输入、范围与输出达成一致 |
| 打通读取 | 主 Skill 指导按需进入局部方法 | 页面纠正字幕落盘；Agent 能读最新 revision 与纠正 | 实际读取能看见人工修改 |
| 完成最小修改 | 方法解释如何只缩短相关开头、处理不够五秒的冲突 | 服务验证时间、范围与版本，原子应用；UI 显示 diff | 目标缩短生效，产品名纠正保留 |
| 做反例 | 加入旧基准、句意截断和保护范围冲突处理 | 交错写入、字幕实例重映射、恢复与重开 | 不能靠更改版本号强行重试，不能破坏非目标 |
| 固定行为 | 整理最小正文、触发与任务证据 | 接预览，记录方法与实现版本 | AC-02/03/04/05 对应检查通过 |

这条功能完成后，方法与工具都获得真实反馈。下一条真实口播粗剪沿同样方式把转写、选段方法、提案和成片一起推进，无需等整个工具库或整个 Skill 库先完工。

### 8.10 Skill 版本与改进

正文变动、描述变动和能力契约变动分别记录。运行任务保存实际加载的方法、来源与 hash、模型配置和相关契约版本。DSH 正文可在后续读取时变化，不能假设旧会话自动冻结方法。

首版使用不可变发布包；在途任务期间不原地修改其方法包，更新在任务边界生效。开发热更新必须显式记录并重启相应测试。后续如需不同任务并行使用不同 Skill 版本，再实现版本化 provider 或等价快照机制。

错误复盘先分类：路由错、信息不足、方法判断错、输出契约错、执行错、验证错。只在方法层确有问题时改正文；时间换算错应改代码。自动 Skill 优化后续先离线候选与评测，不让产品 Agent 直接改生产 Skill。

## 9 工作台与 Agent 的联调方式

### 9.1 联调顺序

先做项目视图、播放器、片段列表与字幕编辑，再逐步完善交互；每个可写控件都调用共同服务。复用原生编辑器时，接入其事务和通知，不能 UI 直接变一份状态、Host 再维护另一份。

第一条真实路径应为：页面打开工程 → 用户改字幕 → 服务生成 revision → 页面收到变化 → Agent 读取最新 revision → revise-edit 提交局部提案 → 页面呈现差异与预览 → 用户可恢复。

Agent 对话可复用 DSH 页面提供的会话入口。选中对象通过实际 Host/Client 通信传入，不以启动一个带提示词的新对话代替连续项目上下文。

### 9.2 选择上下文

选择数据至少表达 projectId、observedRevision、selectionType、稳定对象 ID、范围及其坐标系。来源时间与成片时间必须标明，播放头不等于编辑选择。

Agent 接到选择后校验对象是否仍存在。revision 已变化时重新读取和映射，无法可靠映射就说明需要重新选择。对没有选择的“开头缩短”可结合项目理解目标，但须留下实际作用范围。

### 9.3 状态和反馈

命令提交后依据服务响应与变化事件更新。乐观交互必须能回退，失败时不能保留一个看似已保存的页面结果。预览失效、正在生成、旧版本就绪分别展示。

任务进度、能力就绪和实际产物引用来自统一服务；Agent 的消息可解释它们，但不成为第二事实源。用户接受、否决、撤销或手动修改记录关联 revision，避免从聊天推断永久偏好。

### 9.4 Client 接线证据

DSH 页面扩展按锁定版本验证入口装载、模块依赖、作用域、Host 通信、事件与重连。参考[Client Modules](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/client-modules.md)与[Web Client](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/web-client.md)。

M0 提供页面读取和写入证据，M1 提供共同编辑与重开证据。无独立可视面板的外部工具桥接只算能力接线的一部分，不能计为工作台交付。

## 11 测试、评测与完成证据

### 11.1 验证层次

| 层次 | 检查什么 | 不能替代什么 |
| --- | --- | --- |
| 契约与行为 | 时间、范围、命令、幂等、历史、状态转换 | 不能证明真实媒体和 UI 接线 |
| 适配与集成 | 真实后端、DSH、页面、通知、存储 | 不能证明 Agent 做出正确内容取舍 |
| Agent 与 Skill 任务 | 选择、正文加载、证据、提案、修正与停止 | 不能只用工具 mock 或固定提案代替 |
| 媒体结果 | 解码、帧、字幕、音轨、时间与版本 | 不能独立证明自然度或表达完整 |
| 人工审片 | 内容、自然度、节奏、字幕、音画对应与可接手 | 不能替代机器检查与异常路径 |

测试选择以风险和行为为依据，不为低影响文案改动增加镜像测试。时间、事务、任务恢复和媒体映射必须有针对性的边界验证；通过后不无目的重复扩大运行。

### 11.2 固定 AC 验证清单

编号与 PRD、总览 v2 一致。保存每次测试版本、环境与证据，未实施项标未验证。

| 编号 | 主要执行与证据 |
| --- | --- |
| AC-01 | 同一工程页面读取与真实 Agent 工具读取；比对 projectId、revision 和对象引用 |
| AC-02 | 人工纠正字幕再让 Agent 缩短开头；存前后工程、diff、预览和纠正对应关系 |
| AC-03 | 两个相同旧基准交错提交；一个成功后另一个冲突，不能静默覆盖 |
| AC-04 | 同命令重试、同 ID 不同 payload、恢复旧内容后继续写；比对历史与单调 revision |
| AC-05 | 重启重开、外部媒体丢失和重定位；核对头、内容、历史和任务引用 |
| AC-06 | 真实中文素材按要求选段；回查保留项、来源、顺序、时长冲突与素材缺口 |
| AC-07 | r1 渲染期间修改到 r2；核对 manifest、报告、UI 标记和缓存失效/复用 |
| AC-08 | 同请求重复提交、失败重试、取消处理中、进程中断和重启核对；最多一个未结算 attempt |
| AC-09 | 媒体边界集合；检查支持项正确，不支持明确拒绝，原/工作媒体和字幕映射可回查 |
| AC-10 | 选择、受限组合、切换、缺能力四组样例；实际加载、统一提案、范围与冲突都有检查 |

AC-10 不能用“缺能力时报错了”替代组合和切换测试。第二专项夹具必须产生可检查的行为，并标注只验证架构。

### 11.3 媒体边界集合

覆盖 CFR 与 VFR、30000/1001 等分数 fps、非零起点、手机旋转、缺音轨、静音、中文和空格路径、字幕纠正后重排、重复引用同一素材、切点临近语句边界、断开的外部媒体与未完成文件。

帧网格往返保持帧号；非网格时间检查相应量化误差。音频按采样率、起点、编码延迟和实际策略定义容差。字幕烧录字体与外置 SRT 分别检查。

### 11.4 任务登记与保留集

每个评测任务保存 taskId、素材 hash/引用、要求、保留项与来源、输出规格、预期保护区域、失败注入、验证方式与人工量表。逐步形成约 12 至 20 个明确任务，保留集覆盖主要场景，不只随机留几条。

同一任务可以覆盖多个 AC，但需说明各检查结果。固定方法正文、模型/工具配置、输入与输出记录；模型结果可能非确定，记录重复次数与差异，不能只挑最好一次。

保留任务不参与针对性调参。发现回归时区分内容判断、能力精度、接口和渲染变化，保留失败产物与最小复现。

### 11.5 指标和报告

ASR 分一般转写、关键实体/数字/否定、时间精度与缺失覆盖，写明统计单位、分母和人工参考。关键保留项逐项核对，不用单一 5% 错误率自动决定换模型。

任务记录可交付情况、需人工修正、非目标区域变化、阶段耗时、模型/ASR/渲染成本、资源与失败类型。未测指标留待定；不预填成功率、固定 token 或速度承诺。

每个任务的完成记录包含实际运行命令、退出情况、日志/工程/成片路径、所用版本、通过与未通过项、人工意见。底层单测全绿但真实共同编辑没跑，不能关闭对应集成任务。

## 12 版本、发布与数据演进

### 12.1 分开管理版本

| 版本 | 变化对象 | 发布要求 |
| --- | --- | --- |
| 插件版本 | DSH 包、配置、服务与页面 | 固定精确依赖、运行说明与兼容验证 |
| 项目 schemaVersion | 工程与业务数据结构 | 明确读取旧数据、迁移、备份与失败恢复 |
| revision | 用户工程内容演进 | 单调不复用，绑定编辑历史与成片 |
| capability apiVersion | 统一输入输出和行为 | 实现替换前做契约与真实样例验证 |
| implementationVersion | 具体后端、模型与参数实现 | 用于缓存、生产者记录和质量回归 |
| Skill 版本/hash | 方法正文、路由与资源 | 配套契约、任务结果、变更理由和回退 |

同名不同版本不等于兼容，自动迁移不能覆盖原始唯一副本。预发布工程发生结构变化时，仍需说明旧样例是否可读，不能随意删掉失败证据。

### 12.2 运行环境记录

记录操作系统、DSH 发布版本或 commit、插件、Node/运行时、包管理与 lock、媒体工具构建、模型与权重、字体、硬件、编辑器和外部服务版本。参考仓库的旧依赖不能直接视为目标环境可用。

清楚区分本地工程与外部模型处理。凭据按服务或 DSH 引用，日志不保留原文密钥；能力设置说明会发送哪些媒体或文本。素材获取保留来源、作者与许可引用，不把分析用对标默认剪入成片。

### 12.3 打包验证

发布检查插件装载、页面、工具、五个 Skill 发现与资源路径、依赖就绪、工程读写、一个代表任务、导出与重开。包内方法和资源用不可变版本，避免只在源码目录能读取。

变更涉及时间、版本、任务、字幕或渲染时运行受影响集成与媒体任务；只改某个方法先运行该方法与组合回归，阶段结束联合验收。保留上一可用插件与方法包，工程迁移的回退另按数据策略处理。

## 13 后续扩展怎样接入

### 13.1 新增专项 Skill

选择一个真实目标任务 → 列出已有/缺失能力 → 先验证新能力 → 写方法最小正文 → 接共同提案 → 指定作用和保护范围 → 接工作台回查 → 跑成功、局部反馈、失败及与已有方法组合 → 发布支持范围。

通常只增方法与必要适配器，主 Skill 保持通用选择规则；只有出现新的通用协调问题才改主 Skill。不强求每次新增专项都修改入口大提示词。

### 13.2 对标与搜索

候选搜索、媒体获取、参考分析、应用到自己工程分四个能力链。先做用户给定参考文件，保存时间证据与适用条件；再接平台搜索与候选展示。

对标分析结果是观察与建议，不自动改变工程。应用时仍形成新提案，评估自己的素材缺口。素材库搜索保存来源与用途；URL 获取失败、登录要求和平台不支持返回不同状态。

### 13.3 偏好与学习

P0 先记录项目反馈。后续偏好包含 owner、适用范围、明确确认、值、来源和修订；项目要求优先，可查看编辑删除。一次撤销或一次修改不自动成为全局偏好。

方法改进采用离线候选：失败归因 → 规则或 Skill 候选 → 开发集与保留集比较 → 人工审片 → 决定发布 → 可回退。保存聊天或向量索引本身不构成学习效果。

### 13.4 外部工程与高级媒体

外部格式先支持基本片段、轨道、字幕或音频的可验证子集，逐项报告保留、简化和不支持效果。导出可被软件重新打开后才计作格式支持；生成一个文件不等于互通完成。

变速、转场、多机位、跟踪和画幅重构需要扩展时间/空间映射、预览渲染与验收，不能只加一个 Skill 名称。外部工程回流还需决定导入是否生成新项目或新版本，避免覆盖现有工程。

## 15 ADR、任务卡与交接规则

### 15.1 必要 ADR

| ADR | 决定内容 | 最迟何时形成可执行结论 |
| --- | --- | --- |
| ADR-001 | 主编辑底座、工程所有权与全部写入口 | M0 选型后，M1 schema 固化前 |
| ADR-002 | 原/工作媒体、预览导出与时间策略 | M0 小样后形成路线，M1/M2 随边界验证修订 |
| ADR-003 | 中文 ASR、对齐、精度、资源和成本 | M2-T1 进入正式链路前 |
| ADR-004 | DSH 精确版本、插件/Client/Skill/jobs 接线与依赖 | M0 联合小样后；升级必须重验相关链路 |
| ADR-005 | 存储、历史、原子提交、崩溃恢复与迁移 | M1-T1 至 M1-T4 实施时明确，不拖到发布 |

每份记录写背景、选项、实际样例与命令、观察、决定、后果、未验证项与复审条件。试验结果不足时给下一次能区分假设的验证，不以无变化重复尝试代替决策。

### 15.2 任务卡模板

~~~markdown
### M?-T? 名称
- 目标：一个可独立验收的行为。
- 依赖：任务编号、实际完成情况与必要 ADR。
- 需求：FR 与 AC 编号。
- 输入：素材/工程/版本/场景及契约。
- 实现：需要修改的服务、工具、页面、Skill 与配置。
- 验收：仓库中实际存在的命令、预期结果与异常行为。
- 人工检查：内容、观感、范围和可接手性。
- 证据：日志、diff、工程、产物、方法 hash、环境。
- 完成情况：通过、失败、未验证；不能只写“已实现”。
- 交接：未解问题、已排除原因、下一步与受影响任务。
~~~

### 15.3 开发协作边界

每卡围绕一个行为，可以改完成它需要的实现、schema、适配、页面、Skill 和测试，不以最多三个文件为限制。无关重构和新功能另开卡，保持可审查。

已授权范围内的实现、验证和修复继续推进。影响产品范围、已发布接口语义、工程所有权、数据迁移或显著运行/复用条件的变化，先形成具体可审阅方案再决定。普通内部改动和兼容错误码记录理由即可。

可以在同一开发会话接续多张相关卡，跨会话依靠持久化交接；不能把“另开聊天”当作阶段交付。产品 Agent 与开发 AI 是不同角色，后者不能用自己手工选段替代前者的任务验收。

### 15.4 当前最先执行什么

先建 M0-T1 真实任务登记与 Skill 场景卡，再筛选最多两条编辑路线，做 DSH 页面、真实 Agent 调用、Skill 加载和异步任务联合小样。依据证据完成 ADR 与 M1 卡片。

本轮交付仅为 PRD 和技术手册，没有创建正式 Skill、安装依赖、选择底座或执行产品开发。下一轮实施从上述 M0 证据开始，不把方案文字作为已完成事实。
