# 00 总控：你拿着这些文件怎么推进

- 版本：1.0
- 日期：2026-11-02
- 适用：Video-agent 首版 M0—M3 开发
- 你不需要懂技术；按本文的顺序发文件、收文件、转给 DSH 即可。

## 0. 30 秒版

1. 把 `03` + 三份源文档给 **DSH**，让它只做 M0 开工准备。
2. DSH 返回后，把 `01` + 三份文档给 **WorkBuddy（GLM-5.3）**，把 `02` + 三份文档给 **Codex**。
3. 两边做完，把结果文件路径发给 **DSH** 验收。
4. DSH 通过后，才做 M0-T3；M0-T5 通过后才发 M1。
5. `04` 现在不要发，等 DSH 过门后由 DSH 使用。

## 1. 这个包是什么

这是一个**可直接分发的执行包**，不是又一份产品方案。

- `00` 是给你自己看的操作手册；
- `01` 直接给 WorkBuddy；
- `02` 直接给 Codex；
- `03` 直接给 DSH 创造模式；
- `04` 给 DSH 在阶段门之后生成下一波任务包用，**现在不要发给 WorkBuddy/Codex**。

重要：**现在只发 M0 第一波，不要把所有任务一次发出去。** M1/M2/M3 的任务包必须等 DSH 过门后生成，因为接口、schema、编辑底座都还没定。

## 4. 第一步：给 DSH 的开场话术

把 `03_给DSH_M0_主控包.md` 和三份源文档一起给 DSH，复制下面整段：

```text
请先阅读：
1. 03_给DSH_M0_主控包.md
2. Video-agent总览.md
3. Video-agent-PRD.md
4. Video-agent技术执行手册.md

现在只执行 M0 开工准备，不要进入 M1，不要开始完整工作台：
- 确认/初始化仓库与任务卡目录；
- 产出 docs/tasks/M0-T1.md；
- 产出 M0-T2 的比较维度和候选范围，供 Codex 使用；
- 列出你需要我提供的真实素材、路径和人工确认项；
- 先不要写产品代码。

输出：
- 已创建/修改的文件路径；
- M0-T1 卡的核心内容；
- M0-T2 评分表；
- 需要我回答的问题。
```

DSH 正常会返回：

- 一个 `M0-T1` 任务卡；
- 一个 M0-T2 比较维度表；
- 需要你提供素材的清单；
- 明确说“未进入 M1”。

如果 DSH 直接开始写页面/插件，立即打断它，说：

```text
停。现在只做 M0 开工准备，不写产品代码。请回到 03_给DSH_M0_主控包.md 的第一步。
```

## 5. 第二步：给 WorkBuddy 的话术

把 `01_给WorkBuddy_M0-T1_五个Skill场景卡.md` 和三份源文档一起给 WorkBuddy，模型选 **GLM-5.3、极致模式、1M 上下文**。

复制下面整段：

```text
请阅读 01_给WorkBuddy_M0-T1_五个Skill场景卡.md，以及随附的三份源文档。

只执行 M0-T1 的五个 Skill 场景卡草案：
- 不写代码；
- 不做验收判定；
- 不发明 DSH 工具名或 API；
- 不引用真实个人素材；
- 推断处标 [推断]。

输出一个 Markdown 文件，文件名：
M0-T1_WorkBuddy_五个Skill场景卡.md

完成后只回复我：
1. 文件路径；
2. 五个 Skill 的名称；
3. 你需要我确认的问题。
```

注意：**这一幕不要用 Kimi-K3。** K3 留给 M1-T5 的 UI 组件；现在用 GLM-5.3 读长文档更合适。

## 7. 第四步：你怎么收结果

建一个 `回收/` 目录，按下面命名放：


## 11. 验收 WorkBuddy 产物的标准

合格：

- 五个 Skill 都在：video-editing、footage-intake、revise-edit、render-qa、talking-head-roughcut；
- 每张卡有触发/不触发、输入、输出、步骤、保护与冲突、所需能力、成功样例、反例、人工检查点；
- 引用了 PRD/手册的具体章节；
- 推断标了 `[推断]`；
- 没有编造工具名、API、命令；
- 没有声称“已实现/已通过”。

不合格：

- 五张卡写成五段泛泛的介绍；
- 把 video-editing 写成所有专项的大杂烩；
- 把 talking-head-roughcut 写成所有视频的强制入口；
- 编造 `apply_edl`、`render_video` 之类文档里没有的工具名；
- 没有反例和边界。

不合格就退回：

```text
请按 01 文件的“每张卡必须包含”逐项补齐。不要写代码，不要发明工具名，不要把推断写成事实。
```

## 12. 验收 Codex 产物的标准

合格：

- 最多两条推荐路线；
- 每条有 commit、许可证、实际命令、Windows 依赖、运行结果；
- 有工程写入入口、事务/版本、字幕、片段、预览/导出、重开、DSH 接入的证据；
- 明确标出“未验证/阻断”；
- 证据目录里有日志或命令输出；
- 没有改产品仓库、没有写生产代码。

不合格：

- 只读 README 就下结论；
- 推荐三条以上；
- 没有 commit/许可证；
- 把“能启动”当成“能共同编辑”；
- 直接说“选 OpenChatCut”而不给证据。

不合格就退回：

```text
请按 02 文件的比较维度补齐证据；README 和 star 数不算证据。最多保留两条推荐，并标出未验证项。
```

## 13. 你绝对不要做的事

- 不要把 M1-T5 的 UI 提示词现在就发给 Kimi-K3；props/events 没冻结。
- 不要让 Codex 改 `src/dsh`、`src/client` 接线或 `skills/`。
- 不要让 WorkBuddy 在组件里直接请求服务或保存 project/revision。
- 不要接受“聊天里说完成”但没有文件、命令、日志的交付。
- 不要把真实个人视频、转写、密钥发给 WorkBuddy/Codex 的云端上下文。
- 不要让 Codex/WorkBuddy 判定 AC 通过。
- 不要因为某个 AI 说“可以”就跳过 DSH 复跑。

## 14. 出现问题时怎么处理

| 情况 | 你怎么做 |
| --- | --- |
| WorkBuddy 只给聊天答案 | 要求按文件名落盘；聊天不算交付 |
| Codex 改了产品仓库 | 立即停止，要求还原；只用临时目录做预研 |
| DSH 直接开始写 M1 | 打断，回到 M0 开工准备 |
| DSH 说“没有 DSH API 文档” | 让它先记录精确版本并做最小探测，不要猜 |
| Codex 推荐超过两条 | 要求收敛到两条，其余放“未入选理由” |
| WorkBuddy 编造工具名 | 退回，要求只使用手册 §5.1 的逻辑工具组 |
| 素材不够 | 让 DSH 标“缺失”，不要用假素材补 |
| 结果互相矛盾 | 以 DSH 复跑的证据为准；不能靠投票 |

## 15. 附：DSH 后续任务包模板

DSH 在门后生成任务包时，每份必须包含：

```markdown
### M?-T? 名称
- 主责：DSH / Codex / WorkBuddy
- 目标：一个可独立验收的行为
- 依赖：前置卡号、实际完成状态、ADR
- 需求：FR 与 AC 编号
- 输入：素材/工程/版本/场景/契约
- 冻结契约：接口、类型、错误码、时间单位、边界规则
- 允许修改：精确路径白名单
- 只读：精确路径
- 禁止：越界行为
- 实现步骤：3—7 步
- 验收命令：仓库中实际存在的命令
- 证据格式：命令、退出码、日志、截图、文件 hash
- 人工检查：内容/观感/可接手性
- 完成情况：通过/失败/未验证
- 交接：未解问题、下一步、受影响任务
```

没有“冻结契约”和“允许修改”的包，不准发给 Codex/WorkBuddy。
