# 03 给 DSH：M0 主控包

- 任务范围：M0-T1 至 M0-T5
- 你的角色：技术总控、唯一集成者、M0 阶段门负责人
- 现在不要做：M1 生产实现、完整工作台、五个 Skill 正文、真实 ASR、渲染管线
- 交付：任务卡、比较结论、联合小样证据、ADR 草案、M1 卡、阶段门结论

如果用户最新要求与文档冲突，以用户最新明确要求为准；但涉及产品范围、工程所有权、已发布接口语义、数据迁移的变化，先让用户确认。

## 2. 你的总原则

1. **M0 是证据阶段，不是产品实现阶段。** 不要用“先搭完整框架”替代选型证据。
2. **唯一权威工程。** 页面和 Agent 必须经同一个写入口；不能维护两份可独立修改的时间线。
3. **不猜 DSH API。** 以当前安装的精确版本/commit 为准；ADR-004 记录。
4. **Codex 只做有边界的实现/验证；WorkBuddy 只做有边界的文档/组件/工具。** 最终合并、集成、AC 判定在你。
5. **一卡一证据。** 没有命令、日志、路径、版本的“完成”不算完成。
6. **不要提前做 M1。** M0-T5 未通过，不写生产代码。

## 4. M0-T1：真实素材与任务登记

### 4.1 向用户要素材

最多先要 1—3 段，累计约 10 分钟，1080p 即可。优先：

1. 一段中文口播/产品讲解：包含产品名、数字、否定句、条件/限制说明；
2. 一段教程/操作录屏：有明确步骤和结果；
3. 一段边界素材：手机竖屏/旋转、VFR、缺音轨、中文路径、空格路径中的任意一种。

如果用户没有，记录“缺失”，不要用假素材补，不要下载别人的视频冒充。

### 4.2 每段素材记录

```text
assetId:
原始路径:
sha256:
容器/编码:
时长:
分辨率:
帧率（有理数）:
音频:
旋转/像素比例:
时间原点/异常:
用途:
必须保留项:
```

用实际探测结果，不用扩展名猜。

### 4.3 建任务登记

先建 3 条种子任务，不要一次做 12—20 条：

| taskId | 场景 | 目标 | 必须保留 | 输出 | 主要 AC |
| --- | --- | --- | --- | --- | --- |
| T-A | 口播/产品讲解 | 约 1 分钟 | 产品名、数字、否定、限制 | MP4 + SRT + 工程 | AC-06 |
| T-B | 教程/产品操作 | 保留关键步骤 | 步骤、结果、必要讲解 | MP4 + SRT + 工程 | AC-06 |
| T-C | 媒体边界 | 支持或明确拒绝 | 时间/旋转/音轨映射 | 检查报告 | AC-09 |

每条写清：

- 来源和 hash；
- 用户要求；
- 允许偏差；
- 保留项及来源；
- 预期保护区域；
- 失败注入（后续补）；
- 验证方式；
- 人工量表（后续补）。

### 4.4 选贯穿样例

从 T-A/T-B 中选一条作为贯穿样例，后续 M0-T3、M1-T5、M2-T3 都用它。选：

- 中文内容足够；
- 有明确保留项；
- 时长可控；
- 能覆盖转写、提案、字幕、渲染、审片。

### 4.5 验收 WorkBuddy 的场景卡

收到 `M0-T1_WorkBuddy_五个Skill场景卡.md` 后：

- 检查五个 Skill 是否齐全；
- 检查触发/不触发、输入/输出、保护/冲突、能力、样例、反例；
- 检查是否编造工具名/API；
- 检查是否把推断写成事实；

处理：

- 不合格：列出具体缺口，退回 WorkBuddy；不要自己替它重写全部。

## 5. M0-T2：候选底座比较

### 5.1 先定评分表

用技术手册 §3.1 的维度：

- 共同读写；
- 事务与版本；
- 工程能力（字幕、片段、音频、重开、稳定对象、历史）；
- 预览与导出；
- DSH 接入；
- 运行条件（Windows、依赖、字体、模型、CPU/GPU/内存）；
- 复用条件（源码、依赖、分发、维护成本）。

每项用：满足 / 部分 / 不满足 / 未验证 / 阻断。不要用没有证据的分数。

### 5.2 给 Codex 的范围

- 候选：OpenChatCut、FableCut、Timeline Studio；
- Timeline Studio DSH 插件只作桥接参考；
- 最多两条进入正式小样；
- Codex 只做只读预研，不改产品仓库。

把 `02_给Codex_M0-T2_候选底座只读预研.md` 给用户转发；你只需产出评分表和候选范围。

### 5.3 收 Codex 证据后

逐项核对：

- commit 是否存在；
- 许可证文件是否读了；
- 安装/构建/测试命令是否实际运行；
- 工程写入口是否在源码中找到；
- 事务/版本/通知是否有代码证据；
- 字幕/时间/重开是否有证据；
- Windows 依赖是否记录；
- 未验证/阻断是否诚实。

至少对每条最终候选**复跑一个关键命令**，例如启动、测试、写工程或导出。不能只看 Codex 的结论。

### 5.4 决定最多两条

- 如果两条都有真实证据：选一条最可行的作为 M0-T3 主路线，另一条只作备份；
- M0-T3 先用主路线跑通；主路线通过后，时间允许再补第二条的关键差异，不要两条都全量做；
- 如果只有一条：另一条标“不足”，不要凑数；
- 如果都不成立：考虑自研薄层，但先记录缺口和复审条件，不要直接开写。

## 6. M0-T3：DSH 联合小样

这是 M0 最关键的一步，**只能 DSH 做**。

### 6.1 记录精确版本

```text
DSH 版本/commit:
安装方式:
Node/运行时:
插件加载方式:
Client 入口:
Skill 根:
Jobs API:
```

不要用“最新版”代替精确版本。

### 6.2 最小联合小样

用一个夹具工程，不要完整产品：

1. 插件能加载；
2. 至少一个 Agent 工具能注册并被真实调用；
3. 最小 Client 面板能读到同一个 projectId/revision；
4. 页面修改经共享命令入口写入，不直接改文件；
5. 写入后能收到变化通知/事件；
6. Agent 能读到同一工程的最新 revision；
7. 一个最小 Skill（video-editing 草案）能被发现并加载。

允许硬编码一个片段来验证媒体执行；但必须保留真实 Agent 工具调用和页面共同读写证据。

### 6.3 证据

```text
docs/tasks/M0-T3.md
docs/handoffs/M0-T3_证据.md
docs/handoffs/M0-T3_日志/
docs/handoffs/M0-T3_截图/
```

证据至少包括：

- 版本/commit；
- 插件加载日志；
- 工具调用输入/输出；
- 页面读到的 projectId/revision；
- 写入前后的 revision；
- 变化通知；
- Skill 加载的来源和 hash；
- 失败项和原因。

### 6.4 失败时

如果插件/Client/工具/Skill 任一关键项失败：

- 记录阻断；
- 不要进入 M0-T4；
- 不要用“换个写法绕过”掩盖；
- 更新 ADR-004 草案；
- 给用户明确下一步。

## 7. M0-T4：异步小样

只有在 M0-T3 最小接线成立后做。

### 7.1 目标

验证“业务 job → DSH runtime job → 进度/取消/回读”的映射，不是只验证脚本能跑。

### 7.2 最小流程

1. 提交一个渲染或受控长任务；
2. 创建 businessJob；
3. 创建一个 executionAttempt；
4. 映射到 DSH runtime job；
5. 查询进度；
6. 请求取消；
7. 核对实际停止；
8. 回读产物/日志；
9. 模拟重启后的核对。

### 7.3 状态

至少覆盖：

```text
queued -> running -> verifying -> succeeded
queued -> running -> failed
queued -> running -> cancelRequested -> canceled
running -> needsReconcile（结果不明）
```

规则：

- DSH completed 只代表执行结束，业务进入 verifying；
- 检查通过才 succeeded；
- cancelRequested 不等于已停止；
- 每个 job 最多一条未结算 attempt；
- 结果不明先核对，不重复启动；
- 半成品不发布。

### 7.4 Codex 的边界

Codex 只能在你冻结接口后做：

- 本地长任务进程适配；
- 进程树取消；
- 故障注入；
- 测试夹具。

它不能改业务 job 状态机、DSH 运行桥接、发布门。
