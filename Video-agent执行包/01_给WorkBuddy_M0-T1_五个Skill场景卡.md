# 01 给 WorkBuddy：M0-T1 五个 Skill 场景卡

- 任务卡：M0-T1
- 主责：DSH
- 你的角色：研究/文档支援
- 建议模型：GLM-5.3（极致，1M）；拥堵时用 GLM-5.2 → Kimi-K3 → DeepSeek-V4-Pro
- 如果你在 WorkBuddy 外使用智谱清言：仍按本文件执行，输出 Markdown；它不是 WorkBuddy 内置模型
- 产出：一个 Markdown 文件
- 不允许：写代码、做验收判定、发明工具名/API、引用真实个人素材

## 0. 模型不可用怎么办

模型换了，任务不变。按下面顺序替换，不要因为换模型就扩大范围：

1. **GLM-5.3**：首选；
2. **GLM-5.2**：同族、1M 上下文，最接近的替代；
3. **Kimi-K3**：可用，长上下文和结构化也可以；但它的主战场仍是后面的 UI 组件；
4. **DeepSeek-V4-Pro**：复杂推理强，适合把五张卡写严谨；
5. **GLM-5.3-Flash**：只适合先出草稿，DSH 要更严格审；
6. **智谱清言网页版**：可以当外部写作工具用，把本文件和三份文档上传，输出同样格式的 Markdown；它不是 WorkBuddy 的内置模型，产物仍按本文件验收。

不要用 Hy4 preview 作为最终稿。

## 2. 你的任务

只做一件事：为首版五个 Skill 写**场景卡草案**。

五个 Skill：

| Skill | 作用 | 不能变成 |
| --- | --- | --- |
| `video-editing` | 主 Skill：理解任务、选择方法、协调范围与冲突、组织交付 | 把所有专项细节都塞进来 |
| `footage-intake` | 素材接收：检查素材、组织转写与按需画面、形成摘要和缺口 | 对每个素材无差别跑全部模型 |
| `revise-edit` | 局部修改：读最新版本、限定目标、保护非目标修改、形成局部提案 | 默认重做整片 |
| `render-qa` | 产物验收：按 manifest 检查文件、关键内容和待审片项 | 只看退出码或只看字幕里出现某个词 |
| `talking-head-roughcut` | 口播粗剪：按讲话内容选段、去重复/停顿、组织顺序、保护语义 | 成为所有视频的强制入口 |

这些是**方法层**的场景卡，不是代码模块，不是 DSH 工具，不是另一个 Agent。

## 4. 每张卡必须包含的内容

按下面结构写，每张卡 600—900 字，总长控制在 6000 字以内。

```markdown
## <skill-name>

### 一句话功能
### 触发条件
- 什么时候应该选择它
- 什么时候不应该选择它
### 前置输入
- 项目/版本/素材/转写/能力/选择上下文中，至少需要什么
- 缺什么时必须先补
### 工作步骤
1. ...
2. ...
（5—8 步，写判断点，不写空话）
### 保护与冲突
- 哪些内容不能破坏
- 两个目标冲突时怎么处理
- 什么时候必须回到用户
### 所需能力
- 只写逻辑能力，不写具体供应商
- 缺能力时怎么反馈
### 输出类型
- 简报 / 观察 / 统一提案 / 检查报告
- 是否涉及编辑；涉及编辑必须走统一提案
### 成功样例
- 一个真实任务类型的例子
- 说明为什么这个例子能证明方法有效
### 反例
- 一个最容易犯的错误
- 说明错误会造成什么后果
### 人工检查点
- 哪些内容必须人看/人听/人判断
### 与其他 Skill 的边界
- 什么时候交给别的 Skill
- 不能抢哪些职责
### 来源
- 引用 PRD/手册的具体章节
### 假设与待确认
- 标 [推断]
```

### 4.1 五个 Skill 的特别要求

#### video-editing

- 必须体现：整理简报、选择与组合方法、协调作用范围、处理冲突、推进验收交付。
- 必须写清：它不内置全部口播/卡点/教程细节；专项方法按需加载。
- 必须写清：什么时候只做分析、什么时候形成提案、什么时候停下等用户确认。
- 反例：所有视频都走口播；没加载方法就声称使用；能力缺失仍报完成。

#### footage-intake

- 必须体现：检查素材可用性、组织转写、按需读取画面、形成可回查摘要和缺口。
- 必须写清：不是所有素材都跑全部模型；转写时间精度不足时不能假装能精确切词。
- 必须写清：静音素材、缺音轨、VFR、旋转、中文路径等异常怎么报告。
- 反例：把完整日志塞给模型；把粗粒度时间当成字级时间。

#### revise-edit

- 必须体现：读最新 revision、确认选中对象、限定修改范围、保护人工纠正和其他已接受修改。
- 必须写清：旧基准冲突时重新理解并形成新命令，不能改 payload 沿用旧 commandId。
- 必须写清：字幕重排/裁剪后如何保留纠正；无法可靠映射时要求重新选择。
- 反例：旧基准覆盖；为了缩短开头删掉后面的限制说明。

#### render-qa

- 必须体现：按 renderManifest 检查，不拿当前最新工程验收旧成片。
- 必须写清：文件层、内容层、人工审片层分开；退出码为零/文件存在不等于成功。
- 必须写清：r1 渲染期间编辑到 r2 时，报告只属于 r1；缓存复用也要有验收引用。
- 反例：用 r2 验 r1；字幕出现产品名就断言原声保留。

#### talking-head-roughcut

- 必须体现：按讲话内容选段、处理重复和停顿、组织顺序、保护否定/数字/条件/限制说明。
- 必须写清：它是首个专项，不是所有视频的强制入口；教程/产品视频只在讲话主导时使用。
- 必须写清：素材不足、转写缺失、时间精度不足时怎么退回或降级。
- 反例：为了时长删保留项；截断句意；照搬示例时间码。

## 5. 工具引用规则

可以引用技术手册 §5.1 的**逻辑工具组**，但只能写职责，不要写具体函数名：

- project read
- media intake
- analysis submit/read
- media inspect
- capability list
- proposal validate/apply
- history restore
- render submit
- job control
- artifact verify/read
- feedback record

禁止编造：

- `apply_edl`
- `render_video`
- `get_transcript`
- `save_project`
- 任何文档里没有的 DSH API、CLI、命令、schema 字段

如果要表达“需要某能力”，写“需要 proposal validate/apply 这一组逻辑工具”，不要写“调用 applyProposal()”。

## 6. 绝对不要做的事

- 不要写代码、伪代码、JSON Schema、TypeScript 接口；
- 不要设计数据库、目录结构、插件配置；
- 不要替 DSH 决定编辑底座、存储、ASR 供应商；
- 不要写“已实现/已通过/已验证”；
- 不要引用真实个人素材、真实转写、真实产品名；
- 不要把推断写成事实；推断处标 `[推断]`；
- 不要把五张卡写成五篇产品介绍；
- 不要给每个 Skill 编一个“子 Agent”。

## 7. 输出格式

只输出一个 Markdown 文件：

```text
M0-T1_WorkBuddy_五个Skill场景卡.md
```

文件开头加：

```markdown
# M0-T1 五个 Skill 场景卡（草案）

- 依据：Video-agent总览 v2、PRD 1.0、技术执行手册 1.0
- 状态：草案，待 DSH 验收；不代表已实现
- 作者：WorkBuddy / <实际模型>
```

正文顺序：

1. 五个 Skill 的职责边界总表；
2. 五张场景卡；
3. 跨 Skill 的组合与冲突规则（不超过 800 字）；
4. 待 DSH 确认的问题清单；
5. 来源章节清单。
